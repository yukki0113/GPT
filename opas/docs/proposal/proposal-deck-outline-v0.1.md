## 全体方針

- 提案の主題は「OPAS全画面の再設計」ではなく、実利用で影響の大きい主要導線のスマートフォンUX改善。
- As-Isは最終版で実機スクリーンショットを使用する。生成UIはラフ・構成確認用に限定。
- To-Beは、現行業務ルールを可能な限り維持しながら、情報優先順位・モバイル表示・反復操作を改善する。
- 確認済み事実、ユーザー実利用情報、改善仮説、内部仕様未確認事項を混同しない。

## スライド構成

### 1. 表紙
**大阪市OPAS スマートフォンUX改善提案**

副題: 実利用・実機調査に基づく主要導線の改善案

対象:
- ログイン前トップ
- 空き照会・通常予約
- 抽選申込
- 抽選結果照会・確定

注記: v0.1骨組み。最終版ではAs-Isに実機スクリーンショットを使用。

### 2. 提案要旨

メッセージ:
- OPASの主要機能では、PC向けの情報構造がスマートフォンへ持ち込まれている。
- 実機調査で横長表、長い縦メニュー、後出しエラー、反復操作の多さを確認。
- 制度を大きく変えず、利用頻度と改善効果の高い導線から段階的に改善する。

### 3. 調査方法とスコープ

- 実利用者によるiPhone 16実機調査
- 主要導線を連続スクリーンショットで記録
- 画面遷移・UI監査台帳を作成
- 確認済み事実／公式資料／改善仮説を分離
- 状態変更を伴う操作は必要最小限

調査済み:
ログイン前後、通常予約、予約照会、利用実績、抽選申込、抽選結果照会・確定/辞退、利用者設定変更。

### 4. 実機調査で見えた横断課題

1. スマホで横長表が画面幅を超える
2. 長いメニュー／長文告知が主要タスクの前に置かれる
3. 業務制約が選択後のエラーで通知される
4. 毎月繰り返す抽選申込・結果処理が1件単位で反復
5. 長い登録情報がスマホで全文確認できないケースがある

結論: 個別画面ではなく、スマートフォン向け情報設計の共通課題として扱う。

### 5. ログイン前トップ

As-Is:
- 初期表示からログイン欄までiPhone 16実測で約13スクロール
- お知らせ全文がログイン導線より前に並ぶ

To-Be:
- ファーストビュー近傍に「ログイン」「空き状況照会」
- 重要なお知らせは要約表示
- 通常のお知らせは一覧へ整理

最終ビジュアル:
- As-Isは実機SSを使う
- To-Beワイヤーと左右比較

### 6. 空き照会・通常予約

確認済み現行ルール:
- 同一利用日の複数時間帯は選択可
- 異なる利用日の同時申込は不可

To-Be:
- 利用日を最初に1日固定
- 施設／コート／時間帯を縦カード化
- 同一日の複数時間帯選択は維持
- 複数日不可はUIで事前に防止
- 横スクロール0を目標

注意: 通常予約と抽選申込のルールを混同しない。

### 7. 抽選申込

現行入口:
- 利用目的から絞り込む
- 施設を選択する
- お気に入りの施設で照会する

実利用:
- お気に入りを多用
- お気に入りは施設＋ジャンル（種目）まで固定

To-Be:
- お気に入りを主導線化
- 日付カード＋縦時間帯
- 同一施設・同一種目・同一時間帯の複数日を候補選択
- 各日付は独立申込
- 1申込1区分・1抽選番号を維持
- 複数件を一括確認・登録する方式を検討

### 8. 抽選結果照会・確定

As-Is:
- 横長一覧
- 1件ずつ選択→詳細→確定/辞退→一覧へ戻る
- 確定期限付き処理を件数分繰り返す

To-Be:
- 未処理件数と期限を先に表示
- 1結果=1カード
- 複数件を選択して一括確認
- 個別結果単位を維持したまま一括確定／一括辞退を検討
- 個別詳細ルートも残す

### 9. 抽選業務全体フロー

申込期間中:
お気に入り → 対象月 → 複数日候補選択 → 一括確認 → 各申込へ個別抽選番号

結果発表後:
結果トップ → カード一覧 → 複数件選択 → 一括確認 → 確定／辞退

設計思想:
- 業務データを1件に統合しない
- 1申込1区分、1抽選番号を維持
- 利用者の反復操作だけをまとめる

### 10. 予約照会・取消（簡易改善）

確認済み課題:
- 一覧／詳細とも横長表
- 1件の予約情報把握にも横スクロールが必要

改善方針:
- 1予約=1カード
- 日付、施設、時間帯、状態を優先表示
- 詳細は折りたたみ／詳細画面
- 利用件数、取消件数、利用合計等の有用なサマリーは維持

詳細モックはP1。

### 11. 利用者設定変更（簡易改善）

確認済み:
- 設定変更処理選択は縦長メニュー
- 登録内容確認で長い値がスマホで全文確認できないケースあり
- 当該メニュー内に会員更新／利用者登録継続申請は確認できず

改善方針:
- カテゴリ別グルーピング
- 長い値は折返し・全文表示
- 参照／変更の役割を整理

会員更新制度のオンライン化はUI改善と分離して検討。

### 12. 想定改善効果と評価指標

候補:
- ログイン開始までのスクロール数
- 主要導線の画面数／タップ数
- 横スクロール回数
- 後出しエラー回数
- 同一条件の再入力回数
- 抽選2件目以降の追加操作数

目標例:
- ログイン開始 0〜1スクロール
- 主要予約／抽選画面の横スクロール0
- 複数日不可／複数区分不可等の事後エラーをUIで予防

### 13. 実装方針：段階導入

Phase 1: モバイル表示改善
- 情報優先順位
- 横長表のカード化
- 長文／長値のレスポンシブ対応

Phase 2: 反復操作改善
- お気に入り主導線
- 複数申込候補の一括確認
- 抽選結果の一括処理

Phase 3: 制度・業務プロセス
- 利用者登録／更新
- 本人確認
- 口座関連手続き等のオンライン化を別途検討

### 14. 未確認事項・設計上の注意

- 内部API／DB／採番方式は未確認
- 抽選一括登録の最大件数・トランザクション境界は要件確認が必要
- 通常予約の予約番号発行単位は未確認
- 通常予約側のお気に入り保持範囲は未確認
- オンライン会員更新の有無を全体として断定しない

提案では「確認済み事実」と「改善仮説」を明確に分離する。

### 15. 次のステップ／提案範囲

1. 主要4導線の最終ビジュアルを実機SSベースで整える
2. As-Is / To-Be比較を提案書へ配置
3. タップ数・画面数等の簡易効果測定
4. 実装難易度を「UIのみ／サーバ変更あり／制度変更あり」に分類
5. デモ範囲を確定し、スマホ向け独立モックを作成

最終成果物候補:
- 提案スライド
- 実機証拠索引
- 画面遷移設計書
- 主要画面モック／簡易デモ
- 改修優先順位表

## 現時点のビジュアル運用ルール

- 現在の比較画像はラフ。
- 最終版ではAs-Is側を原則として実機SSに差し替える。
- As-Isの画面内部を生成AIで再構成しない。
- 注釈、矢印、問題箇所のハイライトは追加可。
- To-Be側はワイヤー／モックでよい。
