## 1. To-Beの主導線

1. 抽選申込トップ
   - 「お気に入りから申し込む」を最上位に配置
   - 現行のお気に入りが保持する施設＋ジャンル（種目）をそのまま活用
   - 補助導線として「利用目的から探す」「施設から探す」を残す

2. 対象月選択
   - カレンダーで対象月を選ぶ
   - 抽選申込期間外などは選択不可/説明表示

3. カレンダー/日付カード表示
   - 横長表ではなく日付ごとの縦カード
   - 各日付内に時間帯を縦に表示
   - 1つの日付について1区分を選択
   - 同一時間帯を複数日について候補選択可能

4. 複数日の候補選択
   - 例: 10/3, 10/10, 10/17, 10/24 の11:00〜13:00を4件選択
   - 画面上は『選択中4件』としてまとめる
   - 最大5件などの上限値は業務ルール確認後に確定

5. 申込内容確認（複数件）
   - 選択した各日付を独立申込として一覧化
   - 施設・種目は共通条件として上部に表示
   - 各行に利用日・時間帯を表示
   - 『4件を申し込む』等の一括確定CTAを配置

6. 申込完了
   - 各申込に対して個別の抽選番号を発行
   - 例: 10/3→番号A、10/10→番号B のように1申込1抽選番号を維持

7. 次の申込
   - 同じ条件で別日を申し込む
   - 同施設で別時間帯を申し込む
   - 別施設で申し込む
   - メニューへ戻る

## 2. このTo-Beで維持する現行ルール

- 1申込につき1区分（時間帯）
- 1申込ごとに抽選番号1つ
- 申込上限
- 時間帯任意
- 最終確認

## 3. 新しく提案する操作単位

現行は1件ずつ『選択→確認→申込』を繰り返す。

To-Beでは、**利用者の選択操作だけを複数件まとめる**。

例:
- 同一施設
- 同一種目
- 同一時間帯
- 複数日

を一画面で候補選択し、確認画面で4〜5件の独立申込として並べる。

業務上は1件ずつの申込単位を維持するため、『複数区分を1申込にまとめる』設計ではない。

## 4. 技術検討メモ

一括登録を採用する場合、サーバ側では各申込の業務チェック後、複数件を1トランザクションで確定する方式を候補とする。

留意事項:
- 抽選番号の採番方式
- 同時実行時の競合
- 申込上限の再チェック
- 途中成功を許すかall-or-nothingにするか

現時点では内部仕様未確認のため、UI提案では『複数候補をまとめて確認・登録できる方式を検討』とする。

## 5. モバイルUI原則

- 横スクロールを主要操作にしない
- 日付カード＋縦時間帯
- 選択中件数を常時確認できる
- 制約違反を事後エラーではなく事前制御
- 定型利用はお気に入りから最短で開始
