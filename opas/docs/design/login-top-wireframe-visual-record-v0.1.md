## 1. As-Is側の表現

現行トップはページ上部から長いお知らせが連続し、ログインフォームまでiPhone 16実測で約13スクロール。

ワイヤーでは以下を示す。

1. トップページ冒頭
   - OPAS
   - お知らせ
   - 複数のお知らせ項目

2. お知らせの長い連続表示
   - 多数の告知を縦にスクロール

3. ようやくログイン
   - 利用者番号/パスワード
   - ログイン
   - ログイン不要の照会導線

重要:
- 現行には `ページの最後へ` があるが、目的指向の `ログインへ` CTAではない。
- 約13スクロールはユーザー実測。

## 2. To-Be側の表現

### TB-LOGIN-01 トップページ

ファーストビュー近傍へ主要タスクを移す。

優先順位:
1. `ログイン`
2. `空き状況を照会する`
3. 必要に応じて新規登録/利用案内
4. 重要なお知らせ
5. 通常のお知らせ

設計意図:
- お知らせを削除するのではなく、主要タスクより後ろへ情報再配置する。
- 日常利用者が長文告知を通過しなくてもログイン/空き照会へ進める。

### TB-LOGIN-02 お知らせ要約

重要なお知らせを上部に要約表示。

表示候補:
- タイトル
- 日付
- 1〜2行の要約
- 対象者/期限
- `詳しく見る`

通常のお知らせは最新数件に抑え、全件は一覧画面へ。

### TB-LOGIN-03 お知らせ一覧

全お知らせを別画面/一覧として確認。

この画面は情報を削除するためではなく、一覧性と主要導線を分離するためのもの。

### TB-LOGIN-04 ログイン

認証方式は現行を維持候補。

改善の中心は認証方式ではなく到達距離。

ファーストビューから:
- ログインフォームを直接表示、または
- `ログイン` CTAで同ページ内展開/アンカー移動

のどちらでもよい。

目標は0〜1スクロール相当。

## 3. As-Is → To-Be の比較ポイント

As-Is:
- お知らせが主要タスクより先
- ログインまで約13スクロール
- 情報量は多いがタスク到達性が低い

To-Be:
- ログイン/空き照会を先に配置
- 重要通知は要約して維持
- 通常告知は一覧へ整理
- スマホ1カラム
- 横スクロールなし

## 4. ログイン後更新期限通知との関係

実機では更新期限対象ユーザーに、ログイン後 `利用者更新期限のお知らせ` が挟まることを確認済み。

To-Beでは:
- ログイン前: 一般案内を短く要約
- ログイン後: 対象ユーザーへ個別期限通知

という役割分担を基本案とする。

オンライン更新機能の存在/不存在はこのワイヤーから断定しない。

## 5. 評価指標

- 初期表示→ログイン開始までのスクロール数
- 初期表示→空き状況照会開始までの操作数
- 重要通知の認知
- お知らせ一覧への遷移率

目標:
- ログイン開始: 0〜1スクロール
- 空き照会: 1タップ
- 横スクロール: 0
