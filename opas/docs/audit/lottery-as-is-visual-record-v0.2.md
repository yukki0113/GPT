## 1. 共通入口

ログイン後メニューから「抽選申込」を選択し、照会方法選択へ進む。

照会方法選択には次の3経路がある。

1. 利用目的から絞り込む
2. 施設を選択する
3. お気に入りの施設で照会する

## 2. A: 利用目的から絞り込む

一般的な現行フロー。

照会方法選択
→ 利用目的 大分類
→ 利用目的 小分類（種目）
→ 施設選択（グループ・場所）
→ 抽選対象選択（カレンダー＋時間帯表）
→ 申込内容確認
→ 申込完了

特徴:
- 大分類→小分類→施設選択と段階が多い。
- 複数施設を探す場合には使えるが、毎月の定型利用では手順が長い。

## 3. B: 施設を選択する

ユーザー実利用ではあまり使わない経路。

照会方法選択
→ 施設一覧から選択
→ 利用目的（種目）選択
→ 抽選対象選択

特徴:
- 種目を問わず約40〜50施設が縦に並ぶ。
- 施設一覧が長く、スマートフォンでの探索性が低い。
- 定型利用には不向き。

## 4. C: お気に入りの施設で照会する

ユーザー実利用で最もよく使う経路。

照会方法選択
→ お気に入り一覧
→ 抽選対象選択

お気に入りの保持情報:
- 施設
- ジャンル（種目）

そのため、定型利用では大分類・小分類・施設選択を省略できる。

## 5. 抽選対象選択画面

現行は日付を横軸、時間帯を縦軸にした表形式。

確認済み事項:
- スマートフォンでは横スクロールが必要。
- 1申込につき1区分（時間帯）。
- 複数区分を選択するとエラーになる。
- 同じ施設・種目で別日を複数申し込む場合も、1件ずつ繰り返す必要がある。
- 申込上限超過も操作後のエラーで通知される。

## 6. 申込確定単位

1件の抽選申込ごとに抽選番号が1つ発行される。

例:
- 10/3 11:00 → 抽選番号A
- 10/10 11:00 → 抽選番号B
- 10/17 11:00 → 抽選番号C

現行では、この複数日申込をまとめて選択・確認する機能は確認できていない。

## 7. 現行UIの主要課題

1. 利用目的経路では多段階の画面遷移がある。
2. 施設から探す経路は40〜50施設の縦長一覧となる。
3. 抽選対象選択はPC向け横長表で、スマートフォンで横スクロールが必要。
4. 1申込1区分という制約は、UI上の選択制御ではなくエラーで通知される。
5. 同じ施設・種目・時間帯で複数日申し込む定型利用でも、1件ずつ反復操作が必要。

## 8. To-Be検討への接続

現行のお気に入りはすでに施設＋ジャンルを固定できるため、To-Beではこれを主導線として活用する。

また、現行の1申込1抽選番号という単位は維持しつつ、同一施設・同一種目・同一時間帯の複数日を一画面で候補選択し、複数の独立申込としてまとめて確認・登録する方向を検討する。

これはAs-Isの事実ではなくTo-Be案であり、混同しないこと。
