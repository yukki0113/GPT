# デッキ構築標準手順 — Preflight必須ゲート（2026-11-10）

状態: 運用設計 v0.1。これは**デッキ生成コード実装済みという意味ではない**。M6実装時の優先受入条件。

## 背景・失敗ケース

「海晶乙女をUR0で組みたい」を `STRICT_NO_UR` と誤認して、所持URを候補外とした。修正時も《灰流うらら》3・《無限泡影》3だけを見て、所持DBの**登録全5種類9枚**（《増殖するＧ》1、《墓穴の指名者》1、《抹殺の指名者》1を含む）を一度も全件列挙せず、採用/不採用理由の表を出さなかった。所持DBに載っていないカードを未所持0と推定するのも禁止。

**原則: 毎回デッキ構築前にDB側の所持・規制・カードマスターを全件照合し、採用しない登録済み汎用も理由を残す。** 規制候補で禁止0枚なら採用しない。使用可否が未検証のカードは安全上暫定保留とし、公式情報再検証を要求する。

## 1. リクエスト解釈

- 既定 `LOW_RARITY_CORE`: **テーマ中核の必須UR0 + 新規生成UR0**。確認済み所持URは汎用/出張枠で採用可。
- 「UR0」「URなしで組みたい」は、別途厳格指定がなければ**新規生成UR0**。テーマ中核UR0が成立しない場合は、条件違反・所持次第の別構築を分離して示す。
- 明示的「所持URも禁止」「デッキ全体UR0」のみ `STRICT_NO_UR`。ユーザーの明示要求が既定より優先。
- 採用可能なSR/R/Nの上限、パック/デッキ方針、環境/先後の指定を保持。不要な再質問はしない。

## 2. 必須PRE-FLIGHT（レシピ作成より前）

1. Drive `GPT/MasterDuel/DB/MD_CURRENT_HEAD.json` を取得し、現行HEADのgeneration、ZIP file ID、SHAを読み、ZIPを独立取得して検証。**以前の会話・過去のファイルID・前回のレシピを最新DBとみなさない**。
2. 本番DBをread-onlyで読み、`owned_cards`など正式スキーマから**登録済み所持カードを全件**取得。カードID・名称・所持枚数・登録時点・不明状態・正本SHAを記録。所持未登録は `UNKNOWN`（0枚扱い禁止）。
3. 同じHEADのレアリティ・カード種別・テーマカードIDを参照。M3のMD規制と日時、検証ランクを取得。規制は候補/ゲーム内確認済を区別。
4. M5-A汎用・出張パッケージ、M5-Bテーマ/属性・種族、M5候補の追加sidecarを可能な範囲で読み、どの集合まで取得したか出典・SHAを記録。存在しないsidecarは「未照合」。
5. **登録済み所持全件について、カードIDごとに `ADOPT` / `CONSIDER` / `EXCLUDE` / `REVIEW_REQUIRED` を必ず1件ずつ決める。** 決められない場合は `REVIEW_REQUIRED`。メモ例：所持数が多いが主軸の展開を妨げる、M3禁止候補、所持数制限、役割重複、選定枠不足、サポート不成立。汎用候補は少数の手動リストに限定しない。
6. Preflight監査レコードが欠ける場合、**「DB全件照合済」「所持反映済」「新規UR0確定」等の表現は禁止**。ベストエフォート候補と明記して不足データを提示する。

### preflight監査の入力と出力契約

`build_request`: mode, new_ur_craft_max, theme_core_ur_required_max, sr_allowed, deck_format, as_of, strategy。

`source_pins`: head_generation, head_sha, sqlite_sha, inventory_snapshot, m3_snapshot+effective_on+verification, m4_index_sha, m5_a_sha, m5_b_sha, m5_generic_discovery_sha, source_retrieved_at。未取得は必ず `null` + reason。

`owned_inventory_decisions[]`: **全登録済み** card_id, owned_quantity, rarity, regulation_limit or UNKNOWN, regulation_confidence, disposition, decision_reason, main_or_extra, selected_quantity。選ばない場合も削除しない。

`preflight_status`: `PASS` / `PARTIAL` / `BLOCKED`。 `PARTIAL` の場合は満たした条件のみ断言する。

## 3. テーマ・レシピの構築

1. M5-C/Webでテーマの基本エンジン、始動・コア、EX、動き、縛りを調査。Game8はMD構築・環境の参考、遊戯王カードWikiはカード相互作用・テーマ史の追加参考とし、**双方をゲーム内一次規制に昇格しない**。
2. テーマ最低構成と補助・汎用の枠数を先に確保。必須SR・R・N、必須UR、EXから到達する手段を分ける。
3. 所持汎用の採用可否表を優先して埋め、不足する役割はM5候補から探す。追加URが必要な候補は新規UR0条件では採用禁止（数量UNKNOWNなら `INDETERMINATE`）。強さ・展開適合の理由がある場合は所持URでも見送ってよいが、その理由を書く。
4. MAIN40–60/EX0–15、各カード最大3、規制上限、同名重複、デッキセクション、EX必須カードと展開制約、テーマ役割、カード効果本文、CPをチェックする。M3禁止0候補は使用保留にしてユーザーへの推奨を避ける。
5. 少なくとも**初動の例、最終到達点、妨害/耐性、失った高レア展開、代替案**を検討し、未検証ルートは `REVIEW_REQUIRED`。
6. 記事の掲載デッキと自作アレンジ、提案レシピ、ゲーム内実証レシピの区別を維持。

## 4. 生成後の必須監査

- デッキ内の**所持登録済みカード全件**を採用/不採用で一覧に突合。具体的に「参照済み所持件数」「採用枚数」「見送った理由」を示す。
- カードID、MDレアリティ、枚数、MAIN/EX、各カードの既知・未知所持、必要生成CP（SR/R/N/UR別）を算出。**所持UNKNOWNは未所持と断定せず、費用に上限・暫定・UNKNOWNを付す**。
- `NEW_UR_CRAFT_ZERO`, `CORE_UR_ZERO`, `STRICT_NO_UR` を**独立の結果として**出す。前提が未知ならPASSとしない。
- M3禁止制限の未ゲーム検証、特殊裁定、規制未掲載、M5分類候補の不確実性を保留事項として一覧化。
- 構築の根拠URL、参照日時、DB/SHA、Preflight監査サマリ、改善案、前版との差分を含むprivate成果物として保存し、ソースHEAD・所持DBは変更しない。

## 5. 合成テストの合格条件（M6実装時）

1. 「UR0」要求かつ所有UR3枚あり→`LOW_RARITY_CORE`、所持URを候補プールに含める。勝手に`STRICT_NO_UR`にしない。
2. 所持登録5件のうち2件のみ採用→**5件全件が意思決定表に存在**し、3件には採用しない理由がある。
3. 禁止候補0枚はWeb記事で推奨されてもそのまま採用せず`REVIEW_REQUIRED`または除外。
4. 未登録URの所持枚数UNKNOWNで必要1枚→新規UR0を**PASSにしない**。
5. 所持0枚と所持情報なしUNKNOWNを区別する。
6. HEADのSHA不一致/世代不一致・古いM5索引→Preflightを`BLOCKED`または`PARTIAL`、成功と記載しない。
7. EX15枠・MAIN40枠・規制上限・召喚ロックを越える→完成案として採用しない。
8. 記事に載っているという理由だけでMD現行合法・裁定成立を断言しない。
