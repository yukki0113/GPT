# P0 追補: シークレットパック収録・解放ナビゲーション（2026-11-09）

- 種別: 要件整理・検証計画。**収録データの収集や自動取得の実装は未実施**。
- 基本設計: [BASIC_DESIGN.md](BASIC_DESIGN.md)
- P0判定: [P0_DECISION.md](../audits/p0_202611/P0_DECISION.md)

## 1. 利用者が実現したいこと

「このデッキを作りたい → 必要なカードがまとまって出るパックを回したい → そのパックを解放するために、まず何を生成すればいい？」を逆引きして回答する。

パック収録情報は単なるカードの入手先表示ではなく、**生成CPとジェムを抑えるためのパック解放ナビゲーション**の入力。デッキ必須カードの不足枚数、保有済みカード、生成費用、パック収録と解放条件を一緒に評価する。

## 2. パック種別・排出と解放の仮説（検証状態を保持）

- **シークレットパック**: 1パック8枚のうち共通カードプール4枠 + 当該パックのピックアップ4枠、というゲーム仕様の理解を暫定採用。各個別攻略ページの「収録カード一覧」は **ピックアップ対象一覧の候補** と解釈する。原則、そこに載るSR/URが生成による**解放キー候補**。ただし一覧の完全性や現行ゲームとの一致は**未検証**。解放から24時間という時間条件や例外、無料解放・更新条件は版/例外を含め別途検証する。
- **マスターパック**: 広い共通カードプールで狙い撃ちしにくい。シークレットパックのピックアップがなければ、生成可能なカードは生成を基本提案とする（あくまで推奨アルゴリズム上の扱い）。
- **期間限定パック**: 販売中と終了済みを分け、終了時に「現在そこから引ける」と表示しない。後日別のパックに再収録される可能性を許容。
- **その他**: ストラクチャーデッキ、レガシーパック、配布、生成不可、特別な解放などは上記3分類に押し込めず別種別/例外として保持する。
- 同じカードは複数パックに属しうる。**歴史上収録**・**現時点で排出可能**・**生成可能**・**デッキ合法**は別の真偽/UNKNOWNとして管理する。

## 3. データモデル拡張案（実装前レビュー要）

既存 `packs` と `pack_cards` を基点に、少なくとも以下を区別する。

| 対象 | 推奨フィールド | 主な意味 |
|---|---|---|
| `packs` | `pack_id`, `name_ja`, `kind`, `sale_status`, `available_from/to`, `status_checked_at`, `status_source` | 販売可否は更新時点付き。個人の「未解放」と別 |
| `pack_cards` | `pack_id`, `card_id`, `pool_role` (= PICKUP/COMMON/UNKNOWN), `rarity`, `source`, `checked_at`, `confidence` | 共通4枠の全カードを個別パック専用収録カードと誤認しない |
| `pack_unlock_candidates`（新規概念） | `pack_id`, `card_id`, `condition` (= OBTAIN/CRAFT/UNKNOWN), `status` (= CANDIDATE/SCREEN_CONFIRMED/ACTIVATION_CONFIRMED), `source`, `checked_at` | SR/URピックアップからの推定と実ゲーム解放確認を区別 |
| `pack_unlock_events`（任意・非公開） | `pack_id`, `unlocked_at`, `expires_at`, `observed_state` | 24時間の個人状態とパックの一般販売状況を混同しない |
| `card_acquisition` | `card_id`, `method`, `craftability`, `cost`, `as_of`, `source` | 生成可否は画面で選択中の版と論理カードを区別 |

上記は概念案であり、カードIDの結合単位、例外、ライセンス適合、時点の扱いをP0で確認してから確定する。

## 4. 逆引きの要求・出力

入力: デッキの必要カード/枚数、所持枚数（UNKNOWNを0扱いしない）、利用可能なジェム/CP（任意）、UR新規生成0などの既存モード。

出力: 各候補パックの必要カードの該当SR/UR数・不足枚数、共通枠とピックアップ枠を区別した適合状況、販売・未解放状態、解放可能性、解放に適したSR/UR、生成CP、未確認の出典、推奨順。

推奨はまず「不足している**デッキ採用予定のSR**を生成して解放」、次にデッキ採用予定UR、次に不要なSR、最後に不要なUR。ただしその候補が生成可能であること、既存のUR予算モード違反がないこと、複数パックの重複解放などを考慮。期待開封コストの**確率モデルが未検証**なら、確定的なジェム節約額を捏造しない。

## 5. 取得元の位置付けと検証計画

- ユーザー提示の入口: https://game8.jp/yugioh-masterduel/424875 。個別パックページのレアリティ別「収録カード」は**ピックアップ候補**と位置付ける。サイトの取得許可、再利用条件、現在の一覧とゲーム内収録の一致は未承認/未検証のまま。
- Game8のページを参照できることは、大量自動巡回・保存・再配布の許可を意味しない。robots.txtと利用規約、必要に応じて明示許諾を確認する。アクセス制限の回避はしない。
- ゲーム内ピックアップ一覧は画像表示で全件手作業照合が高コスト。**全パック×全カード画像照合をP0の必須ゲートにしない**。個別ページ2～3パックとゲーム内の数例を比較し、収録一覧がピックアップ枠を示すという仮説を検証する。
- キーカード生成テストは **実際にデッキに必要なカードを生成する機会** に合わせて実施し、検証のためだけのCP消費を要求しない。ある1枚で解放できたことを一覧全件の正しさへ一般化しない。
- 候補データの結果表現は `CANDIDATE` / `SCREEN_CONFIRMED` / `ACTIVATION_CONFIRMED` と区別する。

## 6. 作業範囲・判定

1. **完了**: P0-C固定30件のカード名・MDレアリティ・日本語効果意味の目視照合30/30、選択版の生成UI30/30。これを入手パック30件実見と混同しない。
2. **次のP0小規模調査**: 上記2～3パックの個別ページの収録一覧/レアリティ/解放条件を監査し、取得条件と再利用条件を確認。ライブ販売状況は別出典で管理。
3. **設計のみ可**: 既存の合成fixtureを用いたスキーマ・逆引きアルゴリズムの議論。実ページのデータ取得・大規模台帳化・P1-A1の実カード全文インデックスは権利/運用ゲートを通過するまで **NO-GO**。
4. 作業完了の報告では、画像ベース全件照合・個別ページ全件取得・現行ショップ検証済みと偽らない。

## 7. 出典と区別

- **ユーザー要件**: デッキ→パック→解放生成カードの逆引き、3パック類型、個別Game8ページのレア一覧＝ピックアップ候補、ゲーム内の画像中心表示。
- **監査済み**: 30件のゲーム内カード詳細照合、禁止表示と生成ボタンを別管理する必要性。詳細はP0-C最終監査を参照。
- **今後検証**: 個別Game8一覧の完全性・パック解放候補全件の正確性・実施中の販売/解放条件・アクセス規約。
