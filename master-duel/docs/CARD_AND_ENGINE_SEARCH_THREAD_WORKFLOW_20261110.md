# MDカード・ギミック検索室 — 独立スレッド運用仕様（2026-11-10）

状態: スレッド運用仕様 v1.0（ドキュメントのみ）。既存M1/M4/M5検索を使う。新しい検索APIや自動スレッド生成が完成したという意味ではない。

## 1. 役割と責務の分離

- **カード・ギミック検索室**: カードの意味・条件・関連・出張の候補探索。候補の根拠と制約、MDレアリティと禁止制限の確認、構築側に渡せる短い候補セットを返す。
- **デッキ構築スレッド**: 入力したテーマ・実所持・制約からMAIN40–60、EX0–15の具体的レシピ、生成CP、採用枚数、全所持カードの採用/不採用監査を行う。
- 検索室では、ユーザーから明示されない限り40枚レシピを生成しない。検索室の候補を「実際に採用できる完成デッキ」と同一視しない。

## 2. 情報源の探索順序

1. GitHubの最新mainとREADME、`docs/BASIC_DESIGN.md`、`.gpt/CONTEXT.md`、`.gpt/WORKFLOW.md`、この文書を読み、正本・利用可能なAPI・保存パスを確かめる。
2. 非公開Drive `GPT/MasterDuel/DB/` の現行 `MD_CURRENT_HEAD.json`、SHA整合の取れた正本ZIPを**読み取り専用で**取得する。カード名、日本語効果、MDレアリティはここから。必要に応じM3禁止制限と施行日、M4効果ファセット、M5-Aテーマ・汎用・出張、M5-B属性/種族・名称グループ、M5追加候補sidecarを読む。各sidecarは独立派生索引であり、本番HEADにマージされていると推定しない。
3. まずDBを検索する。その後、最新MD環境・採用判断にはGame8等、効果とカード相互作用・ルールの追加調査には遊戯王カードWiki等を使う。公式MDゲーム内情報・KONAMI告知はMD禁止制限の一次確認先。二次情報を一次情報に昇格しない。
4. 外部記事はサイト利用条件を遵守して**必要ページだけ**確認。許諾不明の大量クロール・本文複製・公開DBへのカード効果実個票の転載は行わない。

### 所持情報の取り扱い

- 単なる「ドローできるN/R魔法」の検索には所持台帳の全件取得は必須としない。所持条件のフィルタを頼まれた時は現行HEADの所持データを検証し、所有未知と未所持を分離する。
- `UR0` は既定で**新規生成UR0**。所持済みURを使った候補は可。明示「デッキ全体UR0」のみ `STRICT_NO_UR`。
- 「所持しているカードから選んで」「この出張の生成CP」のような個人所持依存の問い合わせでは、最新HEAD・所持枚数・規制/CPを再取得。未取得なら費用を確定しない。

## 3. 検索フロー

`REQUEST_PARSE -> SOURCE_PIN -> CANDIDATE_RETRIEVE -> EXPAND -> EFFECT_VERIFY -> REGULATION_CHECK -> RANK -> REPORT`

### REQUEST_PARSE

質問から対象を抽出し、`query_type` を次のいずれか、または組み合わせとする：

- `EFFECT_SEARCH`: ドロー/サーチ/手札交換/墓地回収/蘇生/展開/妨害/除去など
- `PROPERTY_SUPPORT`: 属性・種族・レベル/ランク・攻守・カード種別を利用する支援
- `NAME_SUPPORT`: テーマ名の明示指定、指定カード名扱い、カード名を含まない間接サポート
- `ENGINE_SEARCH`: 出張ギミック・最小セット・MAIN/EX枠・制約・相性
- `COMPARISON`: 複数候補の比較、SR以下、UR予算、既所持のみ、先攻/後攻等
- `FOLLOWUP`: 続く質問では同テーマ・条件を保持し、指示された次元だけ更新

条件は `md_rarity`, `card_kind`, `attribute`, `race`, `level_or_rank`, `effect_action`, `required_state`, `main_extra`, `as_of`, `ownership_constraint`, `budget` 等へ正規化。

### CANDIDATE_RETRIEVE/EXPAND

- M1名称・原文検索で初期カードを得る。効果タグがあればM4から行為・対象・発動条件・コスト・制約を照合。
- M5-Bの「同じ効果句に属性・種族が共起する」候補はあくまで候補。必要に応じレベル/ランク/カード名の支援を独立に調べる。存在しない精密APIの結果を捏造しない。
- M5-A/B/追加汎用sidecarから役割とエンジン候補を追加。登録されていない出張系統は、名前とURLの候補登録だけで具体的セットが完成しているとみなさない。
- 候補が見つからない場合は検索範囲・未索引属性・未実装ファセットを示す。**DB未検出 = カード不存在/採用不能ではない**。

### EFFECT_VERIFY/REGULATION_CHECK

- 上位候補について、**カードの日本語原文に戻り**、その効果の主体、行動、対象、場所、発動条件、コスト、使用後ロック、ターン制限を区別する。
- `DRAW`: デッキから手札にドローする。
- `SEARCH`: 特定カードをデッキから手札へ加える（ドローではない）。
- `EXCHANGE`: ドローと捨てる/戻す処理を組み合わせた手札交換。
- `MILL`: デッキから墓地へ送る（ドローではない）。
- `RECOVER`: 墓地/除外から手札へ戻す（ドローではない）。
- 相手がドロー、自分がドロー、双方がドローを分離。通常ドローと効果処理を分離。
- `ACTIVATION_REQUIREMENT`、`COST`、`OPTIONAL_EFFECT`、`ON_RESOLUTION`、`TURN_LIMIT`、`LOCK`、`OPPONENT_DEPENDENCE` を判定し、条件を満たさない効果を簡単な汎用ドローとして推薦しない。
- MDのレアリティはMDカードマスターで確認。OCGのレアリティと取り違えない。規制は最新施行日と一次確認状態を併記。M3禁止0候補・制限不明はそのまま推奨せずレビュー保留/注記。

### RANK/REPORT

適合度 = 効果の条件一致 + テーマとの作用一致 + 実用可能性 + レア/新規UR予算 + EX枠/召喚ロックの負担 + 根拠の確認度。点数を作っても各成分・不確実性を示す。人気ランキングを合法性や効果成立の証明にしない。

回答は必ず以下を含む：

1. **検索条件**（例：MD、N/R魔法、直接ドロー、規制基準日）。所有状況は参照した場合だけ記載。
2. **候補表**：日本語名、MDレアリティ、種類、働き、必要条件・注意点、推薦理由、確認状態。候補数は実際に確認できた件数のみ。
3. **テーマ/出張特有**：MAIN/EX部品数（判明分）、必要な初動、競合ロック、妨害・補助役割、独立根拠。未確定のセットは未確定と明記。
4. **除外・保留**：強いがUR、効果はサーチでドローではない、規制でNG、記事しか根拠がない等。
5. **監査**：参照したDB版/SHA、根拠URL、調査日時、未確認事項。DBへの追加登録は別指示がある場合か、既存の追記運用が許容する候補sidecarのみ。

## 4. テスト質問

### ケースA：軍貫サポート・出張ギミック

> 軍貫を組みたいがテーマだけではパワー不足。使えるサポートと出張ギミックを教えて。

- まず軍貫の主軸カードとその実際の効果・構築条件を調べる。キーワード一致だけで「軍貫」と付くカードに限定しない。
- ランク4エクシーズ、レベル4、炎属性/水族、通常モンスター指定等を**原文照合して**支援条件として検討（候補が不適合なら除外）。テーマ外カードも候補へ。
- 「単体サポート」と「複数枚セットの出張」を別表で扱う。軍貫側の通常召喚権・EX15・ロック・先攻/後攻・必要URやSRを記載する。
- 出張の現行MD合法性と完成展開は確認状態を区別。「軍貫と相性が良い」を実績と推論に分ける。
- このスレッドだけで完成40枚レシピを自動生成しない。

### ケースB：低予算エグゾディア用N/Rドロー魔法

> 低予算エグゾディアを組みたい。デッキからドローできるN/Rの魔法を教えて。

- `EFFECT_SEARCH`, `DRAW`, `md_rarity IN (N,R)`, `card_kind=SPELL` を原則。永続/速攻/通常魔法を含めるかはカードごとの条件に沿って分類。
- 1枚で即ドローできる、必要コスト/盤面がある、相手依存、手札交換、ターン中の発動制約、ドロー先の限定などを分ける。
- エグゾディア側の手札を集める目的と矛盾しないか判定。単なるサーチやデッキ破壊は直接ドロー一覧に混ぜない。
- 具体的なカードの採用可能枚数をM3に照合する。見つからなかった項目を捏造しない。

### ケースC：継続条件

> 軍貫の候補のうち、新規UR0で扱える出張だけに絞って。

- 前問の軍貫/MD/支援目的を保持。明示された追加条件のみ差し替え。既存所持を参照できた場合のみ「新規UR0確定」と表記。
- 適格パッケージのMAIN/EX、必要枚数、MDレアリティ、所持確認済/UNKNOWN、禁止制限の状態を再照合。

## 5. スレッド間の受け渡し

検索室の出力から、構築室に渡す `CandidateBundle`（保存する場合はprivate）:

`query`, `constraints`, `catalog_sha`, `regulation_snapshot`, `retrieved_at`, `candidates[]`（card_id, role, section, rarity, conditions, effect_evidence, source_urls, verification）, `engine_candidates[]`（parts/alternates/locks/main_extra/prerequisites/verification）, `rejected[]`, `unknowns[]`.

- 構築室はCandidateBundleを「推薦済み確定レシピ」とは扱わず、自身のPreflightで最新所持/規制/HEADを再照合して、採用枚数・CPを決める。
- 検索室からユーザーの所持データを公開GitHubへコピーしない。
- 調査で発見した未索引候補はソースURL・文脈・検証状態を保持し、M5-C private sidecarへ追加することを将来拡張とする。登録完了を偽らない。

## 7. 運用上の境界

- この文書の追加は**検索ロジックの新規実装ではなく、既存ツール利用の手順定義**。M4は確率的/ルールベース候補索引であり意味検索の完全解決器ではない。M5-Bの名称グループ580やサポート候補2,288を確定情報にしない。
- 検索結果・カード情報をpublic Gitに無断で個票化しない。private情報はDriveに管理し、書込時は既存単一ライターとSHA照合を遵守。
- 予算・新規UR0の照会では必ず現在の所持DBとMD規制を参照。所持を問わない一般的なカード検索ではその負荷を強制しない。
