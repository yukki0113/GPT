# マスターデュエル デッキ構築支援AI — 基本設計

- **Version**: v0.1
- **策定日**: 2026-11-09
- **状態**: 初期設計／未実装
- **対象**: 遊戯王マスターデュエル（MD）のみ
- **公開方針**: 当面は個人利用。将来のサービス化は今回の対象外。
- **優先する体験**: 「SR以下で組めるお手軽テーマを、所持カードを活かして探す」

## 1. 目的と非目的

### 目的
1. MD収録カードを可能な限り網羅し、**正式な日本語名・日本語効果文が検索可能**な台帳を構築する。
2. 種族・属性・レベル・ランク・リンク・攻守・カード種別・テーマ等の条件検索に加え、「ドロー」「テーマをサーチ」「召喚権を使わない展開」のような**意味・役割検索**に対応する。
3. MD固有の**N/R/SR/UR、禁止・制限、パック・入手方法**を保持する。
4. 汎用カードと**出張パーツ（エンジン）**を区別して管理し、採用条件と競合制約を評価する。
5. ユーザーの所持カードを再利用し、**新規生成が必要なカードとCP**を評価する。
6. 採用理由・制約・根拠・更新時点・不確実性を説明できるデッキ案を出す。

### 今回の非目的
- 市販サービス、台帳の二次公開、カードデータの再配布。
- 公式ゲームへのログイン／所持データの自動取得（手段・許可未確認）。
- 全カードの裁定を完全に再現するルールエンジン、コンボ成立・勝率の保証。
- データ源の無条件スクレイピング。取得手段・規約・権利を先に確認する。

## 3. 検索・構築のモード定義

「SR以下」は次の**異なる意味**を持つ。検索結果には必ず適用モードを表示する。

| mode | 名称 | URに関する規則 |
|---|---|---|
| `STRICT_NO_UR` | 完全SR以下 | メイン・EXとも、**所持分も含めUR禁止** |
| `LOW_RARITY_CORE` | 低レアテーマ＋所持資産活用（既定） | **テーマ中核のURは不採用**。汎用・出張等のURは**所持済みの範囲のみ**採用可。新規UR生成0枚 |
| `OWNED_UR_ONLY` | 所持URのみ許可 | テーマ内外を問わず、所持URのみ採用。新規UR生成0枚 |
| `UR_BUDGET` | UR生成上限 | 不足URの生成枚数またはCPの上限を指定 |
| `CP_BUDGET` | 総生成CP上限 | N/R/SR/UR別、または総CPを制約 |

- `LOW_RARITY_CORE` の「テーマ中核」の範囲は**テーマ名だけでは定義しない**。初動・展開・終着点・必須EXを含む最小成立セットで評価する。
- 所持数が**未登録／不明**のURを自動で「無料」と判断しない。未確認なら「暫定候補」として不足情報を表示し、**新規UR 0枚確定候補**にはしない。
- 既に所有するカードは複数のデッキで再利用できる。新デッキを組むたびに再生成はしない。
- レアリティがN/R/SRでも、不足枚数と生成CPは集計する。

## 4. データモデル（論理）

実装前に実データの形式を監査し、キーや正規化粒度を最終確定する。以下は概念上のエンティティ。

| エンティティ | 主な項目 | 備考 |
|---|---|---|
| `cards` | canonical_card_id, passcode, kind, attribute, race, level/rank/link, atk, def | 外部ID対応表と別管理。表記差・カード別バリエーションを考慮 |
| `card_names_texts` | card_id, locale, official_name, effect_text, text_version, source, checked_at | **ja-JP必須**。英語は補助。翻訳推測を公式原文と混同しない |
| `md_card_catalog` | card_id, md_available, rarity(N/R/SR/UR), status_as_of | OCG/TCGレアリティと分離 |
| `md_banlist` | card_id, max_copies(0..3), effective_from, effective_to, source | **現在のルールを基準時点付きで評価** |
| `packs` | pack_id, name_ja, kind, available_from, available_to, current_status | 期間限定・過去収録・現行販売を区別 |
| `pack_cards` | pack_id, card_id, source, checked_at | 入手方法と生成可否は別属性 |
| `acquisition_methods` | card_id, method(pack/craft/structure/distribution/etc), status, cost, source | 生成CPと購入可能性を区別 |
| `archetypes` / `card_archetypes` | archetype_id, card_id, relation_type | 直接所属・名称指定対象・関連候補は別 |
| `card_effect_facets` | card_id, action, target, zone, trigger, cost, lock, once_per_turn, confidence | LLM抽出値は暫定タグ、根拠となる原文位置を保持 |
| `generic_cards` | card_id, role, context, rating_source, source_date | 「汎用」は出典付き評価であり絶対分類ではない |
| `engines` / `engine_cards` | engine_id, name, card_id, min/max_copies, required/optional, role | 出張パーツを**セット単位**で管理 |
| `engine_constraints` | engine_id, required_starter, summoning_lock, extra_slot, conflicts, notes | 他ギミックとの制約・競合 |
| `engine_synergies` | engine_id, archetype_or_engine_id, interaction, evidence, confidence | 検証済みと仮説を区別 |
| `inventory` | card_id, owned_count(nullable), known_state, updated_at | **個人データ。公開Gitには保存しない** |
| `deck_proposals` | proposal_id, mode, card_id, quantity, roles, legality_snapshot, cost_snapshot | レシピ、採用理由、計算根拠を再現可能に |

カードの基本属性（レベル・ランク・リンク、攻守、Pスケール等）は、該当カード種に適用されるものだけ設定する。未適用と不明を混同しない。

### 4.1 所持台帳の3状態
- `UNKNOWN`: まだ確認していない。`owned_count = NULL`。
- `KNOWN_ZERO`: 0枚と確認済み。`owned_count = 0`。
- `KNOWN_POSITIVE`: 1枚以上と確認済み。枚数を保持。

所持カードは**汎用だけでなく全カードを登録可能**にする。初期入力対象として汎用カードを優先してよい。CSVインポート・手動修正は将来の実装案。

### 4.2 汎用カードと出張エンジンの差
- **汎用カード**: 単体・少数採用で汎用的な役割を果たしうるカード。役割・評価文脈・出典を持つ。
- **出張エンジン**: 複数枚の組み合わせ、初動・中継・終着点、採用枠、召喚・発動制約等を持つ**再利用可能なパッケージ**。
- 例: 「デモンスミス」「スピードロイド」「壊獣」は、テーマ分類とは**別にエンジン／小パッケージ候補**として管理できる。単体採用と複数枚セットも区別する。
- エンジンは**必須パーツ／任意パーツ／代替パーツ**、メイン／EX別の最低枠、手札事故要因、制約、1枚初動の要否を持つ。
- テーマとの相性は「採用可能」と「強い」「現在合法」を別判定とし、最新の禁止制限と各効果原文で検証する。
- あるカードが「テーマカード」「汎用カード」「エンジン構成員」を**同時に満たしてよい**。相互排他的な分類にしない。

## 5. 自然言語検索パイプライン

1. 質問を意図・制約に分解する（ドロー／サーチ／蘇生／展開、レアリティ、所持、禁止制限、召喚権、必要EX枠等）。
2. 属性等はDuckDBで**厳密フィルタ**。日本語名称・効果文を全文検索。
3. 効果ファセット／テーマ関係／エンジン情報から候補を拡張。「効果文に語が存在しない」カードも対象条件を解析して探索。
4. 必要に応じ意味検索（ベクトル検索等）で再ランキングするが、**意味検索単独で効果の成立を断定しない**。
5. 上位候補について日本語原文を再取得し、コスト・発動条件・対象・制約・ターン1・禁止制限を確認する。
6. 根拠カード、採用理由、不採用理由、未検証事項、台帳時点を回答する。

意味分類の例: 直接ドロー／条件付きドロー／手札交換／サーチ／墓地回収／特殊召喚／除去／妨害／展開補助／リクルート。
「ドロー」と「サーチ」は混同せず、ユーザー意図に沿って関連カテゴリとして提示できるようにする。

### テーマ関連検索
テーマ名を直接指定する効果だけでなく、種族・属性・レベル・カード種・攻守・名称条件等を介して**間接的に対象を取れる**かを検証する。候補は「直接」「条件付き」「推論のみ」に分ける。

## 6. 低レアデッキ発掘アルゴリズム（基本）

1. MD収録中のテーマと候補構築を抽出。**テーマ内UR 0枚**でも成立セットにUR必須なら `LOW_RARITY_CORE` の確定候補から除外。
2. 初動／必要札／テーマ内最小セット／EX終着点を評価。ここはレアリティ表だけでは自動確定できないため、**検証済みレシピや人間確認**を併用する。
3. 汎用札と出張エンジンを組み合わせる際、役割・空き枠・召喚／発動ロック・競合・所持枚数を評価。
4. **MD禁止・制限を先に適用**（各カードのデッキ採用上限）。その上で採用枚数と所持枚数を照合する。
5. `new_needed = max(0, proposed_count - known_owned_count)`。所持不明なら費用は「未確定」とし、0円扱いしない。
6. 生成可能なカードのみ、MDレアリティ別の現行生成CPで不足枚数を積算。パック入手は確率的取得として別の参考情報にする。
7. モードごとのUR条件、SR枚数・CP予算、メイン／EX枚数・ルール制約を確認。
8. 初動の成立、操作難度、妨害手段、事故率（検証方法がある場合）等で比較。「強さ」は**推定・評価根拠・未検証**を明示。
9. 最終提示は**新規UR枚数／UR CP、SR枚数／SR CP、利用する所持UR、必要EX、出張パーツ、パック情報、規制確認日**を含める。

### 所持・制限の例（数字は仮定）
- 所持: 灰流うらら3、増殖するG3、朔夜しぐれ1。
- **例示として**増殖するGの当該適用日時の制限上限が1なら、所持3でも提案採用上限は1。
- 朔夜しぐれは所持1なら新規生成なしで1枚まで採用可能。
- 他のURは「持っている」と確定できなければ、`LOW_RARITY_CORE` の新規UR 0枚確定構築には入れない。
- これらは**例示用の架空スナップショット**であり、2026-11-09現在の禁止制限を保証しない。

## 7. データ源・更新・権利

### ソース候補（採用未確定）
- YGOPRODeck API 等のカード基本情報。
- YGOJSON、yaml-yugi 等のMD関連公開データ。
- 日本語の公式カードDB等による正式名称・効果テキスト照合。
- MD攻略サイト等の汎用評価、レアリティ、収録パック情報。

**着手前監査**: 取得条件／ライセンス／機械取得可否／再利用条件、更新頻度、全収録件数、日本語名・効果の充足率、レアリティ充足率、パック情報の充足率、禁止制限時点を測定する。各属性に出典・照合日・confidenceを記録。日本語原文が得られないカードは欠損として保持し、翻訳推測で埋めたものを正式なテキストとして扱わない。

### 更新設計
- カード・効果テキスト・MD収録・MDレアリティ・パック・禁止制限は**更新周期が異なる**ため、独立更新・差分検出。
- 禁止制限は`effective_from`付きのスナップショットで履歴を残す。
- 過去の収録パックと**現在購入可能なパック**を区別する。
- デッキ案には参照時点のbanlist、カード台帳版、所持更新日を記録する。
- 機械取得できない情報は人手確認待ちにし、勝手に現行扱いにしない。

## 8. ストレージ・セキュリティ

- **GitHub（公開）**: この設計・コード・スキーマ・テスト・公開可能なサンプルのみ。
- **外部非公開保存領域（候補: 非公開Drive等）**: カード台帳の実体（権利・量に応じて判断）、ユーザー所持枚数、私的デッキ等。
- **処理**: Parquet + DuckDBを候補とする。実装時は既存 `tools/data-storage/` のREADMEと契約を読んでから利用する。所持枚数の頻繁な編集にはSQLite等の更新系ストアも検討する。
- 個人の所持情報や外部コンテンツ全文を公開Git、Issue、Actionsログに無断配置しない。
- LLMからの検索は、DB全件を会話に読み込む方式ではなく、SQL／検索ツールで**必要部分だけ取得**する方式。ChatGPTの通常会話にGitを保存するだけでは自動でSQLが動くわけではない。

## 9. 品質・受入基準（初期案）

1. 同一MDスナップショットで、カード件数、主キー重複0、名称・効果・レアリティ・パック充足率をレポートできる。
2. すべての提案でMDの適用日時つき禁止・制限に適合する。
3. 所持数`UNKNOWN`と`0`を区別し、UNKNOWNを理由に「新規UR 0確定」と誤表示しない。
4. `STRICT_NO_UR`でデッキの全カード（EX含む）にURが0枚。
5. `LOW_RARITY_CORE`でテーマ中核URが0枚、所持未確認URを使用せず、新規UR生成0枚。
6. テーマカードと出張エンジン構成員の重複登録を許容し、デッキ内の合計枚数を正しく集計する。
7. ドローとサーチを区別し、条件付き対象カードの効果原文へ遡れる。
8. パックの「過去収録」と「現在購入可能」を混同しない。
9. 新規デッキ提案は必要な生成枚数とCPを再現可能に算出する。
10. 不明・未検証情報を明示し、合法性／強さを無条件に保証しない。

## 11. 未決事項と設計リスク

- 日本語効果文の合法的で継続可能な取得手段と充足率。
- MD固有レアリティ、生成CP、現行パック情報の出典信頼性・更新周期。
- テーマ中核・任意出張の境界をどう定義し、だれが検証するか。
- 汎用評価の採用サイト・評価日・文脈差の扱い。
- 複雑な対象指定・裁定・複合効果の構造化精度。
- ユーザー所持の私的保管場所と取り込みUI（実装前に選定）。
- 提案の強さを何で検証するか（初動確率／手動テスト／対戦実測）。

**重要**: 本書は設計であり、現行カード一覧・規制・パック収録の実測データはまだ取得していない。実装を始める際に**P0のソース監査が先行**する。

## 追補（2026-11-09）: デッキ→パック→解放カード逆引き

従来の「パック・入手方法を保持する」に加え、**デッキを指定すると、不足SR/URを引くために有利なパックと、そのパックを開くために生成すべきSR/URを案内**するユースケースを正式に追加する。共通4枠/ピックアップ4枠というシークレットパックの枠組みは現時点で検証中の仕様仮説とし、ピックアップ掲載SR/URと解放キー候補の対応も候補データとして扱う。パックが未解放であることは販売終了を意味しない。生成可否、解放・販売状態、カードの禁止制限は独立に管理し、UNKNOWNを真偽に変換しない。

追加の論理モデル候補は `pack_cards.pool_role`（PICKUP/COMMON/UNKNOWN）、`pack_unlock_candidates`（情報源と候補/ゲーム画面/実解放の検証段階）、および期間・解放期限の管理。詳細・残課題・検証ゲートは [PACK_UNLOCK_NAVIGATION_P0_20261109.md](PACK_UNLOCK_NAVIGATION_P0_20261109.md) を正本とする。**P1-A1の実データ実装は依然NO-GO**。
