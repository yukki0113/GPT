## 1. 最優先の確認事項

マスターデュエル収録カードの**ほぼ全件**について、下記のうち「確実に取得できるもの」「一部取得できるもの」「取得できないもの」を**実測**して判定する。

| 区分 | 項目 | 必要度 |
|---|---|---|
| 収録 | MDに実在するか、カードID、更新時点 | 必須 |
| 日本語 | 正式カード名、**正式効果テキスト（ja-JP）** | 最優先・必須 |
| 基本属性 | カード種別、属性、種族、レベル／ランク／リンク、ATK/DEF、Pスケール等 | 必須 |
| MD固有 | N/R/SR/URのレアリティ | 必須 |

| 入手 | 収録パック、現行販売状態、生成可否、ストラクチャー／配布等 | 高 |
| 分類 | テーマ所属、汎用評価、出張エンジンの構成元候補 | 中 |
| 出典 | ソースURL、版・取得日、利用条件、信頼度 | 必須 |

**「英語文をLLM翻訳しただけ」を正式日本語効果文と判定してはいけない。**

## 3. 実測手順

### 3.1 利用条件ゲート（取得前）
- 各候補の公式ドキュメント・規約・LICENSE・著作権表示・robots等を確認し、閲覧・サンプル取得・一括取得・ローカル保存・公開Gitへの転載・将来商用利用を**別々に**判定する。
- 権利が不明なら、アクセス制御回避・ログイン回避・逆解析・大量スクレイピングを行わず、**可能な範囲のメタ情報／許された少量サンプルだけ**を記録する。
- HTTPエラー、アクセス制限、禁止条項があれば尊重し、代替ソースへ移る。制限回避のためのローテーションや非公式内部API解析はしない。
- **公開Gitにはカード効果全文、画像、大容量元データ、個人所持カード情報を保存しない。**

### 3.2 スナップショット採取
可能な対象のみ、明記された合法的手段（公開API／配布データ）で取得する。次を記録する。

- 取得時刻（UTC/JST）、取得URL、HTTP状態、ETag/Last-Modified等、配布版・commit SHA（判明する場合）
- 取得バイト数、レコード件数、ユニークID件数、欠損、重複、パースエラー
- MDの収録判定根拠とフィルタの意味（OCG/TCGの全件をMD収録とみなさない）
- ローカルの一時的な取得物にSHA-256を付す。保管先を報告する。保存が許されない元データは処分し、監査数値のみ残す。

### 3.3 ID突合
- `passcode`、`konami_id`、`dbID/CID`、各ソース内部IDを**同一と仮定しない**。クロスウォーク候補を作り、対応付けの根拠を列挙する。
- 1対多・別イラスト・カード名変更・存在しないpasscode等の例外を抽出する。
- 基準母集団を複数置く（例: AソースのMDレコード集合、BソースのMDレコード集合）。**一つのソースを完全正解と断言しない**。
- Aのみ／Bのみ／一致の件数を明記し、突合率は**分母つき**で表示する。

### 3.4 カラム別網羅率・整合性
各ソースおよび統合可能候補について、以下を集計する。

- MD収録レコード総数、canonical候補ユニーク数
- 日本語正式名が取得できた数・割合
- 日本語**効果本文**が取得できた数・割合（効果のないカードは別分類し、`not_applicable`と`missing`を区別）
- MDレアリティ4種の取得数・割合とソース間不一致数
- カード種別、種族／属性、Lv/RANK/LINK、ATK/DEFの取得率（非適用を分母から区別）
- 禁止制限の**実効日を特定できる**件数、過去情報と現行情報の区別
- パック・生成可否の取得率、販売終了・常設・期間限定を区別できるか
- ソースの更新時点と、最新の追加カードへの追従状況

**数値には常に分子／分母／割合／計測定義／採取時刻を添える。**
例: `ja_effect: 9,500 / 10,000 = 95.0%（効果テキストが必要なMDカードを母数とする）` は**形式例であり実測値ではない**。

### 3.5 層化サンプル監査
最小目標**30件**、可能なら**60〜100件**を層化抽出して、独立した信頼できる参照元と照合する。

含めたい区分:
- 通常／効果／儀式／融合／シンクロ／エクシーズ／リンク／ペンデュラム、魔法、罠
- 旧カード／近年追加カード／名称変更・効果改訂が疑われるカード
- N/R/SR/UR、禁止／制限候補、パック入手可能／非入手
- 汎用カードの例: 灰流うらら、増殖するG、朔夜しぐれ
- 出張パーツの例: デモンスミス、スピードロイド、壊獣
- 日本語名が似ているカード、カード名の一部を対象指定するカード

個別サンプルについて、`md_membership / japanese_name / effect_ja / rarity / banlist / pack`ごとに PASS / FAIL / UNKNOWNを付け、**参照根拠と確認日**を残す。
ゲーム内表示を直接確認できない項目を「公式確認済み」に格上げしない。

### 3.6 初期ユースケースへの適合性
まだ検索ロジックは実装しない。ただし、将来実装できるかをデータ項目で評価する。

- 「ドロー」対「サーチ」の分類に足る効果原文があるか
- 「○○テーマをサーチできるテーマ外カード」の対象・制約抽出に必要な情報があるか
- 汎用カード評価が出典・文脈・評価日を伴って取得可能か
- デモンスミス／スピードロイド／壊獣を**セット構成・必要EX枠・ロック**として後から手動・自動登録できるか
- 所持数のUNKNOWN/0/1以上を分けて管理する設計に矛盾がないか
- 「SR以下＋所持URは可＋新規UR生成0＋現行禁止制限」の判定に必要なデータがそろうか

## 5. GO/NO-GO判定方針

- **GO**: 利用条件に沿って継続取得でき、日本語名・日本語効果・MD収録・レアリティ・禁止制限の取得路線が十分に確立。欠損の補填方法を具体化できる。
- **CONDITIONAL GO**: 主要ソースは利用可能だが、未解決の日本語本文やパック等が残る。**条件と欠損規模を明示**してP1の限定範囲を提案。
- **NO-GO**: 合法的に取得できるソースがない、必須項目の網羅率が著しく低い、IDの整合性が確保できない、現行禁止制限を検証できない等。

固定の合格率を推測で置くのではなく、**実測した母集団・欠損の影響・補填コスト**を根拠に提案する。どんな結論でもP0を「実行済」として正確に完了報告する。

## 6. Git操作と失敗時の扱い

- 現行の正本ルールは` .gpt/GITHUB_OPERATION_POLICY.md `。**通常のdocs/CSV/JSON差分はGitHubへの直接書き込み**を優先し、Issue/Actionsを自動起動しない。
- 書き込み前に最新`main`、対象パスの存在、対象blob SHAを確認する。可能なら複数成果物を1 commitとする。
- **force push / force update 禁止**。競合時は最新`main`で差分だけ再構築する。
- ツール権限や安全制限でGit書き込み不可の場合、無理に迂回せず、成果物をダウンロード可能なファイルで提供し、未反映と明記する。
- 実行中の失敗は原因を調べ、可能な範囲で修正／再試行／確認を実施する。失敗した部分の実測を捏造しない。
