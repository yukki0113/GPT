## 標準の作業順序
1. 最新 `main` と repository共通運用規約を確認。本領域のREADME / CONTEXT / WORKFLOW / BASIC_DESIGNを読む。
2. **P0**: データ源候補の取得規約・利用範囲を調査し、サンプルでカードID対応、収録漏れ、ja-JP効果、MDレアリティ、現行入手パック、banlistの時点を監査。充足率と欠損を**実測**してレポート。
3. P0通過後、安定ID・スナップショット・provenance・欠損状態を持つスキーマを確定する。
4. P1/P2: 日本語検索と意味タグの検索品質を小さなケースで検証してから全件へ拡張。
5. P3: 汎用カード、出張エンジン、所持枚数（UNKNOWN / 0 / 数量）を接続する。
6. P4: デッキの合法性、低レア条件、生成CP、テーマ中核・出張制約を評価。
7. P5: 更新差分、回帰テスト、品質レポートを整える。

## 検証優先例
- 「SR以下のお手軽テーマ」: `LOW_RARITY_CORE` でテーマ中核URなし、**新規UR 0**、EX含め規制適合、所持URのみの採用。
- `STRICT_NO_UR`: 所持していてもURを入れない。
- 所持が灰流うらら3／増殖するG3／朔夜しぐれ1の**仮例**: 禁止・制限の適用日時を照合して上限を確定する。古い上限値は使用しない。
- 所持未確認URは新規生成0確定としてカウントしない。
- 「ドロー」と「サーチ」を区別する。
- 「テーマをサーチできるテーマ外カード」を文字列一致以外の条件で検索できる。
- デモンスミス／スピードロイド／壊獣を**パッケージ**として管理し、必要枚数・採用枠・ロック・重複所持・レアリティを計算できる。

## 技術・Git運用
- Git変更は共通ポリシーのB（direct GitHub write、latest main、fast-forward、競合は再読込）を基本とする。
- DuckDB/Parquetの処理・実装変更前に既存 `tools/data-storage/README.md` を確認し、共通実装を再利用する。
- 新規ソース全文や所持枚数を公開repo/Issue/Actionsログに入れない。私的台帳の正本はP0後に決定。
- 新規実装はフェーズごとにテスト・出典・SHA・更新日時を含む監査可能な完了報告を行う。
