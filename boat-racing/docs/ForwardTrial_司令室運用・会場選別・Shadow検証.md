# ForwardTrial 司令室運用・会場選別・Shadow検証

Updated: 2026-09-13

この文書は、競艇note販売プロジェクトの司令室スレッドで行う以下の判断を、会話履歴だけに依存せず引き継ぐための運用正本である。

- 日次の会場選別
- `ForwardTrial_Ver0.1` のControl継続判断
- FT2全R分析と販売選別分析の読み分け
- 仕様改訂候補のShadow検証
- SG/G1、開催日目、新規会場の探索方針

予想そのものの決定規則は `競艇AI予想_2連単1点前向き試行仕様書_Ver0.1.md` を正本とし、本書はその仕様を上書きしない。

- コード・仕様・運用文書: GitHub `yukki0113/GPT` `main`
- 日次CSV: Google Drive `data`

## 3. 会場選別の役割

会場選別は「買うレースを決める工程」ではなく、**当日どの会場の全RをForwardTrialへ通すかを決める探索母集団の設計**である。

したがって、会場選別で強く絞り込みすぎない。最終的な購入・販売候補は、選択会場の全Rを `ForwardTrial_Ver0.1` で評価した後に、A/B/C、1号艇A、2連単適格、販売Scoreで絞る。

会場選別の結果だけでレース単位のA/B/Cや買い目を変更しない。

## 4. 会場選別で見る3層

FT2では、会場評価を少なくとも次の3層に分ける。

1. **全R構造**
   - A/B/C比率
   - 予想軸1着成功率
   - 予想軸成功後の2着候補2艇カバー率
2. **2連単1点適格**
   - 対象産出率
   - 1号艇頭率
   - 2艇カバー率
   - 内側1点成功率
   - 的中率 / ROI
3. **販売選別**
   - 有料 / 無料 / CSVのみ
   - 販売順位帯
   - Score、分離度、軸警戒等の条件別成績

販売候補が0件だった会場でも、全Rの軸・相手構造が良ければ「予想しにくい会場」とは断定しない。逆に、適格ROIだけが高くても少数標本なら本線会場へ即昇格させない。

## 5. 選別原則

- 会場数は固定しない。通常は3〜6場程度を目安とするが、情報量・開催構成・探索目的で増減してよい。
- 会場特性マスタは補助情報・タイブレークに限定し、それだけで採否を決めない。
- 新規・未検証会場を適度に探索枠へ入れ、データがないから永遠に選ばれない自己強化を避ける。
- 開催日目は分析軸であり、初日・最終日を機械的に除外しない。
- SG/G1も分析軸であり、グレードだけで一律除外しない。一般戦と分けて集計する。
- 公式締切時刻は会場選別に使わない。締切時刻は予想・販売freeze後の真正性監査にだけ使う。
- 1日や数Rの好不調で会場を昇格・降格しない。標本数、全R構造、適格後品質を併記する。
- 商品上の無料枠不足を理由に弱いレースを強制採用しない。必要なら探索会場を広げ、候補母集団を増やす。

## 6. 台帳が最新でない場合

会場選別時に直近日の台帳記帳・Atomic Aggregate Setが未完了の場合、その未検証日の数値を採否根拠へ使わない。

1. `FT2_取込管理` と `FT2_集計監査` から最新の真正完了世代を確認する。
2. その最終完了日までのFT2を根拠とする。
3. 未記帳日がある場合は、回答内で「その日は会場選別根拠へ未使用」と明示する。

台帳不調を理由に結果や記憶から手計算で累計を補完し、正式な会場評価へ混ぜない。

## 7. 会場選別CSVの標準形式

司令室から出走表取得工程へ渡す標準CSVは次の4列とする。

```csv
会場,会場CD,開催何日目,位置づけ
```

`位置づけ` は司令室向け説明列であり、出走表取得requestの仕様に不要な場合は取得workflowへ混入させない。

## 8. Controlの固定

現行Controlは `ForwardTrial_Ver0.1` とする。

- 当日結果参照前に予想・販売選別をfreezeする。
- 結果確認後にControlのA/B/C、相手、2連単1点、販売Score、順位、掲載区分を変更しない。
- 単日の不調で同一Verの重みや閾値を途中変更しない。
- 改訂する場合は別versionとして前向きに開始する。

分析で改善余地が見つかっても、既存Controlを過去日に遡及適用して「前向き成績」として扱わない。

## 9. Shadow検証の原則

仕様改訂候補はControlと混ぜず、Shadowとして独立管理する。

Shadowを真正な前向き比較として扱う条件:

1. 結果参照前にルールを明文化する
2. 結果参照前に対象日分をfreezeする
3. Controlと別version / 別列 / 別ファイル等で識別できる
4. Control列を上書きしない
5. 結果後に条件を変更した場合は、その日以前へ遡及しない

結果確認後にControl順位を別区分へ並べ直した分析は探索的バックテストとしては利用できるが、Shadowのforward実績には数えない。

## 10. 現在の研究候補

以下は2026-09-11までの分析から生じた**研究候補**であり、Controlへは未採用。結果前freeze資産が存在しない日はforward Shadow成績として扱わない。

### Shadow-S: 販売境界

候補設計:

- 販売順位1〜3位: 有料
- 4〜6位: 無料
- 7位以下: CSVのみ

目的は、上位3本と4〜6位の性能差、および無料導入品質を前向きに比較すること。

### PairGate

2着候補側の失敗を抑えるための候補。特に、

- 2連単相手が5〜6号艇
- 2着候補分離度
- 軸警戒
- 2着本線一致

等を販売抑制条件として検証する。少数標本を根拠に即時完全除外しない。

### OpponentScore再研究

現行Opponent Scoreの重み変更はControlへ直入れせず、1号艇が実際に勝ったレース等を研究母集団として、2〜6号艇の2着選定性能を別途検証する。艇番・コース位置の効果を調べる場合も、結果分析と予想入力を混ぜない。

## 11. 仕様改訂判断

改訂判断ではROIだけを見ない。

- 予想軸1着率
- 2艇カバー率
- 内側1点成功率
- 最終的中率 / ROI
- 販売順位帯
- 候補本数
- 少数標本・高配当1件依存
- 一般 / G1 / SG
- 会場 / 開催日目

を分けて確認する。

特に、問題が「軸」「相手2艇」「内側1点」「販売順位」のどこにあるかを切り分け、複数層を同時に変更しない。
