競艇AI予想：出走表取得依頼の定型作業

対象となる依頼文
------------------
mm/dd について、下記の会場の出走表の取得をお願いします。

会場,会場CD,開催何日目,位置づけ
…
…

「位置づけ」は会場選別側の運用メモであり、出走表取得requestの必須値ではない。ユーザーが取得対象として列挙した行は、明示的な除外指定がない限りすべて取得対象とする。


0. 正本の確認
--------------
1) GitHub `yukki0113/GPT` の latest `main` を確認する。
2) 以下を順に確認する。
   - `boat-racing/README.md`
   - `boat-racing/.gpt/CONTEXT.md`
   - `boat-racing/.gpt/HANDOFF.md`
   - `boat-racing/.gpt/WORKFLOW.md`
   - `boat-racing/docs/README_出走表取得.md`
   - `boat-racing/src/fetch_boatrace_racelist_with_meta.py`
   - `boat-racing/src/fetch_boatrace_racelist.py`
   - `boat-racing/src/fetch_boatrace_event_meta.py`
   - `boat-racing/src/enrich_boatrace_racelist_metadata.py`
3) D. Actions-Native Executionを使う場合だけ、`.github/workflows/boatrace_racelist_issue.yml` のrequest parser / validationを確認する。
4) 日次CSV、ログ、キャッシュ、台帳はGit管理対象外であり、ソース正本の代わりにしない。


1. 依頼内容の受領・入力確認
----------------------------
1) mm/dd を対象年を含む `YYYYMMDD` へ確定する。
   - 年をまたぐなど年が一意に定まらない場合だけ確認する。
2) ユーザーが表に列挙した会場を取得対象とする。
3) 各対象会場について、会場名・2桁会場CD・開催何日目を確認する。
   - `最終日` はそのまま運用上のday表現として扱う。
4) `位置づけ` は取得対象の説明用であり、Actions requestの `venues[].name/code/day` へ混入させない。
5) 以下の場合は公式サイトへアクセスする前に停止し、入力不備として扱う。
   - 実在しない日付
   - 会場名と会場CDの不一致
   - 会場CDの重複または不正値
   - 開催何日目の不正値


2. 実行経路の判定
------------------
1) GitHub運用方針に従い A/B/C/D を判定する。
2) BOAT RACE公式サイトへChatローカルから正本fetcherと同一条件で通信できる場合は C. Pure Deterministic Execution を優先する。
3) Chatローカルから公式サイトへ通信できず、正本fetcherを同一条件で再現できない場合は D. Actions-Native Execution とする。
4) Dの場合はIssueを1 requestにつき1回だけ作成する。
   - title: `[BOATRACE_RACELIST_REQUEST] <request_id>`
   - body: Markdown fenceを付けないraw JSON object
   - required: `date`, `venues[].name`, `venues[].code`, `venues[].day`
   - optional: `request_interval_seconds`（通常1.0）
5) RESULTが返らない途中状態では、重複Issueを早期に作成せず、既存Issue / runの状態をAで再確認する。


3. 公式出走表・開催メタの取得
------------------------------
標準入口は `fetch_boatrace_racelist_with_meta.py` とする。

1) `fetch_boatrace_racelist.py` で各会場1R〜12Rの公式出走表を取得する。
2) PC版を優先し、解析不能時だけスマホ版へフォールバックする。
3) HTTP 200だけでは成功扱いにしない。日付・会場・会場CD・開催日目・艇番1〜6・必須選手情報等を検査する。
4) `fetch_boatrace_event_meta.py` / `enrich_boatrace_racelist_metadata.py` で公式日別レース一覧から会場ごとの開催グレード・開催名を付与する。
5) 公式から安全に解決できない値を推測補完しない。
6) 展示、直前情報、オッズ、人気、結果、払戻、外部予想は参照・混入させない。
7) 公式サイトへの負荷を抑えるため通常取得は直列とし、`request_interval_seconds` を守る。Retry-After / backoffを尊重する。


4. 現行CSV仕様
---------------
予想入力CSVは21列とする。

追加メタデータ:
- `開催グレード`: `SG` / `G1` / `G2` / `G3` / `一般`
- `開催名`: 節全体の公式開催タイトル

既存列:
- 各Rページの公式タイトルは既存の `レース種別` に保持する。
- 重複する `レース名` 列は設けない。

原本CSVは33列とする。

正常な公式空欄はそのまま保持するが、必須項目欠落・艇番不足・キー重複・公式識別情報不一致・開催メタ解決不能は成功扱いにしない。


5. 完了条件・検証
------------------
取得後、対象全体について少なくとも以下を確認する。

- 対象会場数 × 12R の取得状況があること
- 各Rが艇番1〜6を各1件持つこと
- `日付 + 会場 + R + 艇番` が一意であること
- 予想入力CSVが21列であること
- `開催グレード` / `開催名` が存在し全行非空であること
- `レース種別` が存在し非空であること
- `レース名` 列が存在しないこと
- 禁止情報（予想、展示、オッズ、結果、払戻等）が混入していないこと

D経路ではIssueコメントの `BOATRACE_RACELIST_RESULT` を正本の完了通知とし、以下を確認する。

- `status == success`
- `task_exit_code == 0`
- `validation_exit_code == 0`
- `success_races == expected_races`
- `input_rows == 対象会場数 × 12 × 6`
- `input_columns == 21`
- `metadata_columns == [開催グレード, 開催名]`
- `errors == []`
- run conclusionがsuccess
- RESULT記載のartifactが実在し期限切れでないこと

`partial` / `failure`、validation error、列不一致、取得不足は正常完了として扱わない。


6. Artifact回収と日常の受け渡し
--------------------------------
Actions artifactには監査用として予想入力CSV、原本CSV、取得状況CSV、ログ、resolved_request、validation report等を含めてよい。

ただし日常のユーザー向け完成物は **予想入力CSV単体** とする。

標準手順:
1) artifact ZIPを内部作業用として回収する。
2) ZIPを解凍する。
3) `YYYYMMDD_公式出走表_会場名_会場名….csv` を予想入力CSVとして特定する。
4) CSVの行数・21列・対象日・会場集合を再確認する。
5) 通常の回答ではこの予想入力CSVだけをこのスレッドへ出力する。
6) ZIP、原本CSV、取得状況CSV、ログ、resolved_request、validation reportは診断・監査が必要な場合だけ提示する。

ChatGPT Libraryへの保存機能がその時点で実際に利用可能なら予想入力CSVを保存してよい。ただし保存操作を実行・確認できない環境では「Libraryへ保存済み」とは報告しない。その場合も、予想入力CSV単体をこのスレッドから取得できる形で返す。

日次CSVはGitへcommitしない。長期正本保存はGoogle Drive `data/racecards` の別保全工程で行う。


7. 完了報告の定型
------------------
正常完了時は、次を簡潔に報告する。

- 対象日・会場名
- 成功R数 / 期待R数
- 出力行数
- 21列であること
- `開催グレード` / `開催名` 付与済み
- validation errorの有無
- 予想入力CSV単体へのリンク

通常はZIPやログのリンクを併記しない。

異常時は、次を明示する。

- 対象会場・R
- 取得状態（取得不能 / 一部取得 / validation failure）
- 公式応答・解析・メタ付与・workflowの具体的な失敗理由
- 未完成CSVを予想入力の正常な完成物として使用してはいけないこと


8. スレッド引越し時の復元
--------------------------
会話履歴がなくても、latest `main` の以下から復元する。

1) `boat-racing/.gpt/HANDOFF.md`
2) 本定型作業
3) `boat-racing/docs/README_出走表取得.md`
4) `boat-racing/src/fetch_boatrace_racelist_with_meta.py`
5) Dの場合は `.github/workflows/boatrace_racelist_issue.yml`

未完了の日次requestがある場合は、過去会話の「待ち」状態を信用せず、GitHub Issue / ActionsのRESULT・run・artifactを再確認する。累積の直近日付やrun IDは本ファイルへ固定せず、GitHub正本から再取得する。


9. ソース改修が必要になった場合
----------------------------------
1) latest `main` を基準に、既存CSV互換性と現行21列仕様を守って改修する。
2) Python、対応README、必要なtests / workflow / HANDOFFへの影響を同時に確認する。
3) 保存済みfixtureまたは実日付で回帰確認する。
4) 日次CSV、ログ、キャッシュ、台帳はcommitしない。
5) UTF-8テキスト変更は B. Git Change とし、Git更新だけのIssueを作らずdirect writeする。
