# JRDB ファイル相関・キー定義

> Project Sources参照用の整理版。  
> 「整理版_JRDB_固定長データ定義.md」と「整理版_JRDB_マスタコード定義.md」を基に、
> JRDB主要ファイル間のキー、リンク関係、コード参照関係を実装目線で整理したもの。
>
> **重要:** 本資料では、原本にリンク用途が明記されているものを「原本明記」、
> 複数仕様に共通して存在する項目構成から安全に結合できるものを「共通キー」、
> DB設計上の扱いやすさのために提案するものを「実装推奨」と区別する。

---

## 1. 対象ファイル

| ファイル | 内容 | 主な粒度 |
|---|---|---|
| `BAC` | 番組データ | 1レース |
| `KYI` | 競走馬データ | 1レース × 1頭 |
| `CHA` | 調教本追切データ | 1レース × 1頭 |
| `CYB` | 調教分析データ | 1レース × 1頭 |
| `SED` | 成績データ | 1レース × 1頭 |
| `SKB` | 成績拡張データ | 1レース × 1頭 |
| `ZED` | 前走データ | SEDと同一フォーマット |
| `ZKB` | 前走拡張データ | SKBと同一フォーマット |

## 2. キーの基本構造

### 2.1 レースキー

主要ファイルに共通して存在する基本キー。

```text
場コード 2BYTE
年       2BYTE
回       1BYTE
日       1BYTE
R        2BYTE
```

論理上は以下の5項目で1レースを識別する。

```text
race_key = 場コード + 年 + 回 + 日 + R
```

固定長上では合計8BYTE。

`日` は TYPE `F` で、16進数表現（数字または小文字アルファベット）を使用する仕様があるため、
**数値化して再構成せず、原値の1文字を保持することを推奨**する。

### 2.2 馬単位キー

`KYI / CHA / CYB / SED / SKB` は、レースキーに加えて `馬番` を持つ。

```text
race_horse_key = race_key + 馬番
```

論理上は以下の6項目。

```text
場コード + 年 + 回 + 日 + R + 馬番
```

これは「そのレースに出走する1頭」を識別するための共通キーとして扱える。

### 2.3 競走成績キー

`SED` と `SKB` には以下が存在する。

```text
血統登録番号  8BYTE
年月日        8BYTE (YYYYMMDD)
```

原本ではこの16BYTEを **競走成績キー** とし、
「競走馬データとのリンクに使用」と明記されている。

```text
result_key = 血統登録番号 + 年月日
```

`KYI` には「前走1～5競走成績キー」が各16BYTEで格納されるため、
過去走への直接リンクに利用できる。

### 2.4 前走レースキー

`KYI` には前走1～5について、各8BYTEの `前走Nレースキー` も存在する。

```text
前走1レースキー
前走2レースキー
前走3レースキー
前走4レースキー
前走5レースキー
```

これは「どのレースだったか」を引くためのキー。

一方、同じ前走について `前走N競走成績キー` もあるため、

```text
前走レース全体を識別 → 前走Nレースキー
前走した当該馬の成績を識別 → 前走N競走成績キー
```

と役割を分けて扱う。

## 4. 結合関係一覧

| From | To | キー | 関係 | 根拠 |
|---|---|---|---|---|
| `BAC` | `KYI` | `race_key` | 1 : N | 共通キー |
| `BAC` | `CHA` | `race_key` | 1 : N | 共通キー |
| `BAC` | `CYB` | `race_key` | 1 : N | 共通キー |
| `BAC` | `SED` | `race_key` | 1 : N | 共通キー |
| `BAC` | `SKB` | `race_key` | 1 : N | 共通キー |
| `KYI` | `CHA` | `race_key + 馬番` | 1 : 0..1想定 | 共通キー |
| `KYI` | `CYB` | `race_key + 馬番` | 1 : 0..1想定 | 共通キー |
| `SED` | `SKB` | `race_key + 馬番` または `result_key` | 1 : 0..1想定 | 共通項目＋原本リンク項目 |
| `KYI` | 過去 `SED/ZED` | `前走N競走成績キー = result_key` | 1 : 0..1 | 原本明記 |
| `KYI` | 過去レース | `前走Nレースキー = race_key` | 1 : 1 | 原本項目 |
| `ZED` | `SED` | 同一項目構造 | 同形式 | 原本明記 |
| `ZKB` | `SKB` | 同一項目構造 | 同形式 | 原本明記 |

### 注意

`CHA` と `CYB` は対象馬ごとの調教データだが、
原本には「KYIと1対1」とは明記されていない。
欠損・未提供があり得るため、DB上は **LEFT JOIN前提** とするのが安全。

同様に `SKB` も補助データのため、`SED` に必ず存在するとは決め打ちしない。

## 5. ファイル別の主キー・外部キー整理

### BAC

**推奨主キー**

```text
PK: race_key
```

**役割**

- レース基本条件
- 発走時間
- 距離
- 芝・ダート・障害
- 右左・内外
- 種別・条件・グレード
- レース名
- 頭数
- 馬券発売フラグ
- WIN5フラグ

他の馬単位ファイルに対する「レースヘッダ」として扱いやすい。

---

### KYI

**推奨主キー**

```text
PK: race_key + 馬番
```

**主要な外部リンク**

```text
前走1競走成績キー ─┐
前走2競走成績キー  │
前走3競走成績キー  ├→ SED / ZED の result_key
前走4競走成績キー  │
前走5競走成績キー ─┘
```

```text
前走1レースキー ─┐
前走2レースキー  │
前走3レースキー  ├→ 過去レースの race_key
前走4レースキー  │
前走5レースキー ─┘
```

その他、原本で以下が明記されている。

```text
騎手コード   → 騎手マスタ
調教師コード → 調教師マスタ
```

ただし、今回整理対象のProject Sourcesには騎手マスタ・調教師マスタの仕様そのものは含まれていない。

---

### CHA

**推奨主キー**

```text
PK: race_key + 馬番
```

同一対象馬の `KYI` と結合する。

主なコード参照:

```text
調教コースコード → 調教コースコード表
追い状態         → 追い状態コード表
```

---

### CYB

**推奨主キー**

```text
PK: race_key + 馬番
```

同一対象馬の `KYI` と結合する。

`調教タイプ`、`調教コース種別` 等について、
固定長仕様では「調教分析データ内容の説明」参照となっている。
今回の整理資料にはその別説明資料は含まれていないため、
本資料だけでは全コード値を確定できない。

---

### SED

**推奨主キー**

用途により2種類を保持する。

```text
PK候補1: race_key + 馬番
PK候補2: result_key = 血統登録番号 + 年月日
```

RaceNoteのようなレース単位取得では `race_key + 馬番` が扱いやすい。

一方、KYIの「前走競走成績キー」とリンクするため、
`result_key` にも UNIQUE INDEX を付けることを推奨する。

**原本明記の外部リンク**

```text
騎手コード   → 騎手マスタ
調教師コード → 調教師マスタ
```

---

### SKB

**推奨主キー**

```text
PK: race_key + 馬番
```

または

```text
UNIQUE: result_key = 血統登録番号 + 年月日
```

`SED` と同じ対象競走馬の補助情報として扱う。

主なコード参照:

```text
特記コード → 特記コード表
馬具コード → 馬具コード表
脚元コード → 脚元コード表
ハミ       → 馬具コード表
蹄鉄       → 馬具コード表
蹄状態     → 馬具コード表
ソエ       → 馬具コード表
骨瘤       → 馬具コード表
```

---

### ZED

原本に、

```text
データフォーマット、データ内容は、成績データと同一
```

と明記されている。

したがって、解析時のスキーマは `SED` と共通化できる。

```text
ZED schema = SED schema
```

用途上は「対象開催の競走馬に対応する前走情報」として扱う。

---

### ZKB

原本に、

```text
データフォーマット、データ内容は、成績拡張データと同一
```

と明記されている。

したがって、

```text
ZKB schema = SKB schema
```

として共通パーサーを使用できる。

## 6. コード表との相関

### JRDBデータコード表

主に以下から参照される。

```text
KYI
  ├ 脚質
  ├ 距離適性
  ├ 上昇度
  ├ 調教矢印コード
  ├ 厩舎評価コード
  ├ 蹄コード
  ├ 重適性コード
  ├ クラスコード
  ├ 印コード
  ├ 馬記号コード
  ├ 展開記号
  └ 休養理由分類コード

BAC
  ├ 種別
  ├ 条件
  ├ 記号
  ├ 重量
  └ グレード

SED
  ├ 馬場状態
  ├ 異常区分
  ├ コース取り
  ├ 上昇度コード
  ├ クラスコード
  ├ 馬体コード
  ├ 気配コード
  ├ 天候コード
  └ レース脚質
```

### 個別コード表

```text
CHA
  ├ 調教コースコード → 調教コースコード表
  └ 追い状態         → 追い状態コード表

SKB / ZKB
  ├ 特記コード → 特記コード表
  ├ 馬具コード → 馬具コード表
  └ 脚元コード → 脚元コード表
```

系統コード表は今回の8固定長ファイル中に、
直接「系統コード」として参照される項目が確認できない。
別の血統・マスタ系データで利用されるものとして保持する。

## 7. RaceNote向け推奨取得順

1レースをGPT向けに整形する場合は、以下の順で組み立てると扱いやすい。

```text
1. BAC
   └ race_key でレース条件取得

2. KYI
   └ race_key で全出走馬取得

3. CHA / CYB
   └ race_key + 馬番 で調教情報付与

4. ZED / SED
   └ KYI.前走N競走成績キー から過去成績取得

5. ZKB / SKB
   └ 同じ result_key で過去の特記・馬具・脚元・コメントを付与

6. コード表
   └ 生コードを表示名・意味へ展開

7. GPT向けMarkdown / JSONへ整形
```

### 推奨JOINイメージ

```sql
BAC
LEFT JOIN KYI
  ON BAC.race_key = KYI.race_key

LEFT JOIN CHA
  ON KYI.race_key = CHA.race_key
 AND KYI.umaban   = CHA.umaban

LEFT JOIN CYB
  ON KYI.race_key = CYB.race_key
 AND KYI.umaban   = CYB.umaban
```

過去走は固定的な `JOIN` よりも、
KYIの前走1～5競走成績キーを順に解決する方が自然。

```text
KYI.prev_result_key_1 → SED/ZED.result_key
KYI.prev_result_key_2 → SED/ZED.result_key
...
KYI.prev_result_key_5 → SED/ZED.result_key
```

## 8. SQLite格納時の推奨キー

原本の固定長値は変えず、
DB内部で検索しやすい派生キーを追加する。

```text
race_key_raw
result_key_raw
```

を必ず保持し、必要なら別途、

```text
venue_code
year
meeting_no
day_raw
race_no
horse_no
blood_registration_no
race_date
```

を列展開する。

### 推奨INDEX

```sql
BAC : UNIQUE(race_key_raw)

KYI : UNIQUE(race_key_raw, horse_no)
      INDEX(prev_result_key_1)
      INDEX(prev_result_key_2)
      INDEX(prev_result_key_3)
      INDEX(prev_result_key_4)
      INDEX(prev_result_key_5)

CHA : INDEX(race_key_raw, horse_no)

CYB : INDEX(race_key_raw, horse_no)

SED : UNIQUE(race_key_raw, horse_no)
      UNIQUE(result_key_raw)

SKB : INDEX(race_key_raw, horse_no)
      INDEX(result_key_raw)
```

### 理由

RaceNoteでは通常、

```text
指定レース → 全馬 → 調教 → 前走1～5走
```

の方向で辿る。

そのため高速化の中心は、

```text
race_key
race_key + 馬番
result_key
```

の3種類になる。

## 9. 実装上の注意

### 9.1 `日` を10進数前提にしない

レースキーの `日` は TYPE F。

```text
0-9
a-f
```

を取り得るため、文字列として扱う。

### 9.2 レースキーは文字列保持を優先

場・年・回・日・Rを整数に分解してから再生成すると、
先頭ゼロやTYPE Fの扱いを壊す可能性がある。

原本8BYTEをそのまま `race_key_raw` として保持し、
検索用の分解列を別に持つ構成が安全。

### 9.3 result_keyも原値保持

競走成績キーは

```text
血統登録番号 + YYYYMMDD
```

の16BYTE。

前走リンクの基準になるため、
加工前の文字列を保持する。

### 9.4 ZED/ZKBは別テーブルでも共通パーサー

```text
ZED = SED形式
ZKB = SKB形式
```

なので、読み取りコードは共有できる。

ただしファイルの役割は異なるため、
SQLiteでは

```text
sed
zed
skb
zkb
```

と物理テーブルを分けるか、

```text
source_type
```

を持たせて統合するかは実装選択。

### 9.5 マスタ未収録のリンク

固定長仕様には以下が明記されている。

```text
騎手コード   → 騎手マスタ
調教師コード → 調教師マスタ
```

今回のProject Sources整理対象には、
これらマスタ仕様は含まれていない。

したがって現段階では、
「リンク先が存在すること」までを定義し、
具体的なマスタ項目・主キー構成は未定義とする。

## 10. 最小相関まとめ

RaceNote実装でまず覚えるキーは3つ。

```text
race_key
  = 場 + 年 + 回 + 日 + R
  → レース単位

race_horse_key
  = race_key + 馬番
  → 今走の馬単位

result_key
  = 血統登録番号 + 年月日
  → 過去1走単位
```

関係は次の形に集約できる。

```text
BAC
 ↓ race_key
KYI
 ├→ CHA / CYB          : race_key + 馬番
 └→ 過去 SED / ZED     : 前走競走成績キー = result_key
                         ↓
                    SKB / ZKB
```

この3キーをDB内で壊さず保持すれば、
「対象レース → 出走馬 → 調教 → 前走1～5走 → 前走拡張情報」
というRaceNoteの基本経路を構築できる。
