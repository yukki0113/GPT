# JRDB Training Research Parquet / DuckDB 移行判断

監査日: 2026-09-16

## 1. 対象

主対象:

```text
jrdb_training_research_2010_2023_development_lite_v0_1.zip
```

現行の実体は SQLite Research Base を LZMA ZIP で搬送・保管する構成である。

関連正本・実装:

- `horse-racing/jrdb/docs/Training_Research_Base_v0_1.md`
- `horse-racing/jrdb/schema/jrdb_training_research_schema_v0_1.sql`
- `horse-racing/jrdb/src/build_jrdb_training_research.py`
- `horse-racing/jrdb/src/analyze_jrdb_training_stage1b.py`
- `horse-racing/jrdb/config/storage/training_research.example.yaml`
- `tools/data-storage/README.md`

## 2. 結論

**Parquet への移行は技術的に可能であり、長期保存・分析用途の正本として適性が高い。**

一方で、現行実装は SQLite を直接生成・参照する箇所があるため、既存 ZIP を Parquet に変換して Drive 上のファイルだけ差し替えるだけの「ゼロ改修置換」は不可である。

推奨する移行方針は以下。

1. 当面は既存 SQLite builder を維持する。
2. 完成・監査済み SQLite から `tools/data-storage` を使って Parquet を生成する。
3. 研究・分析 consumer を SQLite 直読みから DuckDB / Parquet 読みへ切り替える。
4. SQLite と Parquet の完全同値性と主要クエリ性能を監査する。
5. 同値性確認後、新規運用の長期保存・分析正本を Parquet とする。
6. 既存の frozen SQLite ZIP は過去研究の再現証跡として削除せず archive 扱いとする。

## 3. SQLite 固有依存の確認

### 3.1 Training Research Base の生成

`build_jrdb_training_research.py` は現時点で SQLite に強く依存している。

主な依存:

- `sqlite3.connect()`
- `ATTACH DATABASE`
- SQLite schema script
- `ROW_NUMBER()` / `LAG()`
- `julianday()`
- SQLite UDF `combined_record_hash`
- `PRAGMA integrity_check`
- SQLite index / view の生成

したがって builder 自体を DuckDB / Parquet native に変更する場合は一定の実装修正が必要になる。

ただし、これらは「SQLite でなければ Training Research Base を計算できない」という意味ではない。現行 builder が SQLite を中間 materialization として採用しているためであり、同等処理は DuckDB / Arrow 系へ移植可能である。

### 3.2 Stage 1b 等の研究分析

`analyze_jrdb_training_stage1b.py` は SQLite の `training_runner` を SELECT して Python 側へ読み込んだ後、縦比較ロジックを Python で実行している。

SQLite 固有なのは主に入力 reader であり、以下の科学ロジック自体は SQLite に依存しない。

- same horse の strictly-prior chronology
- same CHA course + furlong 比較
- self percentile
- strictly-prior Official RunPerf median
- sensitivity / Spearman / paired-horse / yearly stability

そのため consumer 側は比較的小さな変更で Parquet + DuckDB 経路へ移行可能である。

## 4. Schema / provenance 上の注意

Training Research Base は `training_runner` 一表だけではない。

現行 SQLite には少なくとも以下がある。

- `training_runner`
- `meta_training_research_build`
- `source_archive`
- secondary indexes
- `v_training_development`
- `v_training_holdout_locked`

`training_runner` のみを Parquet 化して SQLite を削除すると、生成 provenance や frozen research evidence の一部が弱くなる。

したがって Parquet 移行時は、少なくとも次の情報を保持すること。

- builder version
- schema version
- source Git commit
- source Index DB SHA256
- source Official RunPerf DB SHA256
- RunPerf formula / version
- build period / split
- source archive provenance
- source member provenance
- row-level composite hash
- canonical key

metadata は別 Parquet、JSON manifest、audit JSON のいずれかで保持してよいが、`training_runner` だけを唯一の成果物としない。

## 5. `tools/data-storage` との適合性

共通ツールは現在すでに以下をサポートしている。

- SQLite table -> Parquet streaming conversion
- ZSTD / Snappy
- DuckDB SQL
- row count validation
- schema hash
- canonical-key uniqueness
- NULL / min-max validation
- SQLite vs Parquet benchmark
- machine-readable audit JSON

さらに JRDB 用に以下の雛形が存在する。

```text
horse-racing/jrdb/config/storage/training_research.example.yaml
```

現行設定案:

```yaml
source:
  format: sqlite
  table: training_runner
  batch_size: 50000

target:
  format: parquet
  compression: zstd
  partition_by: []

keys:
  canonical: [race_key, horse_no]

sort_by: [race_date, race_key, horse_no]
```

したがって、Parquet 変換基盤を新規に JRDB 内へ複製実装する必要はない。

## 6. Partition 判断

Development Lite 規模では、まず **単一 Parquet + ZSTD** を基準とするのが妥当。

理由:

- 数百 MB 未満の分析データである。
- 過剰 partition はファイル数を増やす。
- DuckDB は単一 Parquet でも column pruning / predicate pushdown を利用できる。
- 共通ツールの現在の guidance も low hundreds of MB では unpartitioned 開始を推奨している。

年別 partition 等は実測 benchmark で明確な利点が出た場合のみ採用する。

## 7. 収集・Raw 系への影響

`jrdb_training_research_2010_2023_development_lite_v0_1.zip` の Parquet 化は、JRDB Raw の取得方式そのものには影響しない。

Training Research Base は概ね以下の下流 materialization である。

```text
JRDB Raw
  -> Index Base
  -> Official RunPerf
  -> Training Research Base
```

したがって「Parquet にすると JRDB の収集ができなくなる」という技術的制約は確認されなかった。

ただし現行 builder は Index Base / Official RunPerf の SQLite を `ATTACH` して Research Base SQLite を生成するため、**生成工程の SQLite まで同時撤去する場合は別の移行作業が必要**である。

今回の目的が長期保存・分析効率・Drive 容量削減であれば、生成工程の SQLite を直ちに撤去する必要はない。

## 8. 既存 frozen artifact の扱い

既存:

```text
jrdb_training_research_2010_2023_development_lite_v0_1.zip
```

は過去研究時点の frozen / reproducibility artifact として扱う。

このファイルは当時の SQLite schema、index、view、metadata と一体で研究結果を再現できるため、Parquet 移行後も historical evidence として保持することを推奨する。

今後の operational / analytical canonical を Parquet に変更することと、既存 frozen evidence を消すことは分けて考える。

推奨構造:

```text
legacy frozen evidence
  jrdb_training_research_2010_2023_development_lite_v0_1.zip

new analytical canonical
  jrdb_training_research_2010_2023_development_lite_v0_1_parquet/
    training_runner.parquet
    metadata / provenance
    conversion_audit.json
```

## 9. 容量面の注意

元 SQLite 本体は Development Lite で約 325 MB、LZMA ZIP transport は約 89 MB だった。

したがって、SQLite 本体と Parquet を比較して小さくなることは期待できても、**既に高圧縮された約 89 MB の ZIP より Parquet ZSTD が必ず小さくなるとは限らない。**

Parquet の主な利点は容量だけではなく、以下も含む。

- ZIP 展開不要
- 列単位読み込み
- predicate pushdown
- DuckDB から直接 SQL
- 分析時の全 DB 読み込み回避
- 共通 storage utility による監査経路統一

そのため最終判断は容量と query benchmark の双方で行う。

Parquet 自体は外部 ZIP しない。外部 ZIP は range / column access の利点を失わせるため、共通 storage policy とも一致しない。

## 10. 移行 PoC の合格条件

Parquet を新規正本へ昇格させる前に、少なくとも以下を確認する。

### データ同値性

- row count 完全一致
- column contract 一致
- canonical key `race_key + horse_no` 重複 0
- canonical key set 完全一致
- year / data_split count 一致
- NULL count 一致
- relevant min / max 一致
- Official RunPerf coverage 一致
- provenance field 一致
- source hash semantics 一致

### 科学ロジック非回帰

- Stage 1b population 一致
- self percentile 結果一致
- primary eligible count 一致
- Spearman 一致
- high-low spread 一致
- paired-horse result 一致
- yearly result 一致

Stage 2b や Training Edge の過去再現で Development Lite を入力に使う経路がある場合、その主要 result も同値確認対象とする。

### 性能

最低でも以下を SQLite / Parquet で比較する。

- full row count
- year filter
- horse chronology
- horse + course + furlong chronology
- trainer chronology
- training pattern group aggregation
- Stage 1b input scan

warm / cold の median を記録する。

## 11. 最終判断

判定:

```text
PARQUET_MIGRATION_TECHNICALLY_FEASIBLE = true
SQLITE_REQUIRED_FOR_LONG_TERM_ANALYTICAL_STORAGE = false
CURRENT_SOURCE_CODE_CHANGE_REQUIRED = true
RAW_COLLECTION_BLOCKER = false
IMMEDIATE_SQLITE_BUILDER_REMOVAL_REQUIRED = false
LEGACY_FROZEN_SQLITE_DELETE_RECOMMENDED = false
PARQUET_POC_RECOMMENDED = true
```

要約すると、**Training Research Development Lite は Parquet 移行候補として適している。**

ただし安全な移行単位は「SQLite builder を全廃すること」ではなく、まず「完成 SQLite から Parquet を生成し、保存・分析 consumer を DuckDB / Parquet 化すること」である。

この段階で科学ロジックと収集系を変える必要はなく、入出力 storage boundary の移行として進められる。
