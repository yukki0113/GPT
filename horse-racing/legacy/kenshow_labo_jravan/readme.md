## 1. プロジェクト概要（何を作っているか）

個人用の競馬データ基盤 + オフライン閲覧・検索・集計ができるPWA「検証ラボ」を開発している。

狙いは以下：

- **PC（ローカル）**：SQL Serverでフルデータ保持・加工・検証・指数算出を行う（自由条件での分析）
- **外出先（競馬場/スマホ）**：オンライン検索は行わず、PC側から「使いそうな範囲」だけ切り出した **SQLiteスナップショット** を端末に転送し、PWAで **sql.js** を用いて端末内で自由検索・集計する
- データは **端末内完結（私的利用）** に寄せ、公開（GitHub Pages）にはデータを置かない（UIのみ公開）

## 3. 主要な定義・仕様

### 3.1 二層構成（全体アーキテクチャ）
- **PC（SQL Server）**：フルデータ保持、集計、指数算出、検証の中心
- **スマホ（PWA + sql.js + SQLite）**：端末内のSQLiteを読み込み、自由検索・集計・表示
- **GitHub Pages（docs/）**：UIのみ（データは置かない）

### 3.2 データ公開方針（重要）
- **生データ・指数データともに GitHub Pages に置かない**
- データは **SQLiteファイルとして端末へ転送**（AirDrop / iCloud Drive等）し、PWAで読み込む
- 端末内完結（私的利用）を徹底する

### 3.3 スマホ側のDB設計方針（配布SQLite）
- 配布SQLiteの主テーブルは **`entries`（1出走＝1レース×1馬のフラット表）**
- **指数も同じSQLiteに同梱し、`race_id` / `horse_id` 等でJOINできる形**にする
- 目的：スマホ側は **SQLを書いてJOIN・集計するだけ**で完結（UI実装が単純になる）

### 3.4 PWA（フロント）実装方針
- iOS/Chrome環境を踏まえ、SQLite読み込みは **`<input type="file">` でファイル選択**が基本
- sql.jsでDBをメモリ上にロードし、検索・集計を実行
- 永続更新は主目的ではない（閲覧・集計中心）

### 3.5 週末出馬表データの扱い
- HTTPで自動取得→race_id.html保存

## 4. 決定事項と未解決事項

### 決定事項（確定ルール）
- GitHub Pagesは **UIのみ**。データ（生データ・指数）は置かない
- スマホは **端末内完結**：SQLiteファイルを転送してPWAで読む
- 配布SQLiteの主テーブルは **entries（1出走フラット）**
- 配布SQLite生成は **C#**で実装（既存C#ソリューションにプロジェクト追加）
- 更新方式はまず **都度全量生成**を推奨（増分更新は痛みが出てから）

### 未解決（保留・今後詰める）
- 配布SQLiteの分割単位
  - まずは「用途別に単一ファイル（例：2〜3場×直近5年）」推奨
  - 端末負荷が出たら「場×期間」分割へ
- PWAの画面/機能の優先順位（MVP定義）
  - MVPは「ファイル読込→フィルタ→レース一覧→レース詳細（出走馬＋指数）」
  - 馬詳細、保存フィルタ、集計は段階的追加
- 配布SQLiteの列一覧・インデックス（スマホ体感に直結）
  - entriesに何を入れるか、どのインデックスが必須か
- 週末出馬表の「手動保存→解析→反映」運用の詳細
  - 保存命名規則、差分反映（idempotent/UPSERT）のキー設計
